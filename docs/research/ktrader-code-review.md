# K-Trader × AI 브리핑 접목 — 코드 리뷰 및 설계 판단

작성일: 2026-08-20
대상: `K-Trader_v10-feature-split-buy-v2` (v10.7.0 / 내부 마커는 v11까지)
목적: 클라우드에서 생성되는 일일 증시 브리핑을 근거로 한국 주식 스윙 후보를 선정하고, K-Trader에 접목해 자동매매를 구성할 수 있는지 판단

## 0. 결론 요약

| 항목 | 판단 |
|---|---|
| 신호 주입 지점 | **있음. 매우 좋음.** `_on_real_condition()` 단 하나로 매수가 통일돼 있어 ~15줄로 접목 가능 |
| 클라우드↔로컬 통신 | **있음.** `signal_emitter.py`가 이미 아웃바운드 WebSocket으로 조건식 신호를 클라우드에 송출 중. 역방향 recv만 추가하면 됨 |

| 즉시 착수 가능 여부 | 가능. 단, 아래 4개 선결 과제 해결 후 |

## 1. 시스템 구조 (실측)

```
[UI 프로세스]  ui_dashboard.py  ── IPC 서버(127.0.0.1, 포트 자동할당, NDJSON, 인증 없음)
      │ spawn + 포트 전달
      ▼
[엔진 프로세스] engine.py (4,006줄, 단일 클래스 TradingEngine)
      ├── 키움 OpenAPI+ QAxWidget (COM, 32bit, 싱글스레드)
      ├── tr_scheduler.py  ── 모든 주문의 단일 깔때기 (TR 250ms / 주문 100ms, 매도 우선)
      ├── signal_emitter.py ── 아웃바운드 WebSocket → 클라우드 Trader_service (송신 전용)
      └── database.py (SQLite, %LOCALAPPDATA%\K-Trader\data\ktrader_history.db)

[웹 프로세스]  web_monitor.py (Flask, GET 전용, DB·상태파일만 읽음, 엔진과 직결 안 됨)
```

주요 사실:

- 매수 진입 경로는 **키움 조건검색식 하나뿐**입니다. 사용자가 종목을 직접 지정해 매수시키는 경로는 코드상 존재하지 않습니다. IPC 명령 15개 중 `MANUAL_BUY`가 없습니다(`MANUAL_SELL`은 있음).
- 조회하는 키움 TR은 5종뿐입니다 — `opt20001`(업종지수), `opw00001`(예수금), `opw00018`(잔고), `opt10074`(당일실현손익), `opt10075`(미체결). **차트 TR(`opt10080`/`opt10079`)이 없어 과거 시세를 가져올 수단 자체가 없습니다.**

## 2. 매수 파이프라인 — 접목 지점

### 2.1 유일한 정문

```
_on_real_condition(code, event_type="I", cond_name, cond_idx)   # engine.py:2489
```

`event_type == "I"` 진입 후 **13개 게이트**를 순차 통과해야 매수 대기열(`_pending_buy`)에 오릅니다.

| # | 게이트 | 라인 |
|---|---|---|
| 1 | `is_trading` | 2504 |
| 2 | `_portfolio_synced` (크래시 후 한도 무력화 방지) | 2510 |
| 3 | 동일 (code, cond) 3초 디바운스 | 2521 |
| 4 | 이미 보유 중 | 2561 |
| 5 | 블랙리스트 (수동=전역, 자동=출처 조건식만) | 2576 |
| 6 | `max_rebuy` 누적 손절 횟수 한도 | 2599 |
| 7 | `rebuy_cooldown_min` 재진입 쿨다운 | 2603 |
| 8 | `_pending_buy` 중복 (우선순위 높으면 교체) | 2615 |
| 9 | `calendar.is_trading_allowed()` — 09:00~15:15 | 2633 |
| 10 | `_check_loss_limit()` 일일 손실한도 | 2638 |
| 11 | 지수 필터 (KOSPI/KOSDAQ 등락률) | 2645 |
| 12 | 전역 보유한도 `max_hold` | 2662 |
| 13 | 조건식별 보유한도 `max_hold_per_cond` | 2670 |

통과 시 `_pending_buy[code]` 등록 + `SetRealReg` → 첫 체결 틱 수신 시 `_on_real_data`(2809)가 실제 발주.

### 2.2 왜 여기가 최적인가

1. **이미 내부에서 직접 호출하는 선례가 있습니다.** `_fire_deferred_condition`(engine.py:2701)이 `self._on_real_condition(code, "I", cond_name, cond_index)`를 그대로 호출합니다. 즉 "가짜 조건식 이벤트 주입"은 이 코드베이스가 스스로 하고 있는 일입니다.
2. **`cond_name`은 실제 등록된 조건식일 필요가 없습니다.** `get_condition_param()`(config_manager.py:620)이 조건식별 → 글로벌 → DEFAULT 순 4단 폴백이므로, `"AI_브리핑"` 같은 임의 문자열을 넘겨도 정상 동작합니다. `config["condition_params"]["AI_브리핑"]`을 만들면 **AI 신호 전용 익절/손절/분할매수/보유한도 프로파일**을 즉시 부여할 수 있습니다.
3. **`cond_idx`는 이 메서드 안에서 한 번도 사용되지 않습니다.** 아무 정수나 무방.
4. 통과하면 분할매수, 분할매도, HARD-STOP, 자동 블랙리스트, 조건식별 성과 집계가 **전부 무료로 따라옵니다.**

### 2.3 최소 변경 경로

| 순서 | 작업 | 변경량 |
|---|---|---|
| 1 | `_process_command`(engine.py:1628)에 `INJECT_CANDIDATES` 분기 추가 → 각 종목에 `_on_real_condition(code, "I", "AI_브리핑", 0)` 호출. `APPLY_SETTINGS`가 이미 `json.loads(args)`를 쓰는 선례(1648) | ~15줄 |
| 2 | `config["condition_params"]["AI_브리핑"]` 프로파일 설정 | 설정만 |
| 3 | `START_TRADING`을 빈 args로 발행 → 키움 조건식 없이 AI 신호 단독 운용 가능 | 0줄 |

**건드리면 안 되는 곳:** `_on_real_data`(2758) 발주 블록, `_execute_sell`(3319), `_on_chejan`(3446). 예수금 SSOT와 체결 정합성이 여기 걸려 있습니다.

## 3. 클라우드 → 로컬 통신 통로

| 후보 | 방향 | 새 포트 | 인증 자산 | 엔진 직결 | 판정 |
|---|---|---|---|---|---|
| **signal_emitter WS 역방향** | 아웃바운드 | 불필요 | JWT 존재 | O | **최적** |
| 파일 드롭 + `_sync_routine` 폴링 | — | 불필요 | 없음 | O (500ms 타이머 기존) | 차선, 단순 |
| ipc.py 명령 확장 | 루프백 | 불필요 | **없음** | O (단 UI가 서버라 외부 접속 부자연) | 조건부 |
| web_monitor POST | 인바운드 | 5000 | 취약한 Basic Auth | **X (별도 프로세스)** | 비추천 |
| notifications | 단방향 Webhook | — | — | — | 불가 |

`signal_emitter.py`는 이미 `websocket.create_connection()`으로 클라우드에 접속해 조건식 편입/이탈 신호를 송출하고 있습니다(engine.py:2495~2502). 핸드셰이크 `{"op":"HELLO","token":JWT}` → `{"op":"ACK","last_seq":N}` → 이후 `{"op":"SIG",...}` 송신. **`_run()` 루프(signal_emitter.py:166~172)가 `send()`만 하고 `recv()`를 하지 않을 뿐, WebSocket은 이미 양방향입니다.** recv 처리(`op == "CMD"`)를 추가하면 클라우드→로컬 명령 채널이 즉시 생깁니다. seq 기반 replay, 영속 버퍼(`signals.ndjson`), 재접속 로직도 이미 있습니다.

주의: `notifications.py`에 **텔레그램 코드는 없습니다.** Discord Webhook + SMTP뿐입니다(`CLAUDE.md:15`의 "텔레그램/디스코드"는 사실이 아님). 브리핑 파이프라인의 텔레그램과 K-Trader의 알림은 완전히 별개 채널입니다.

## 4. 정량 지표 — 여기가 진짜 문제

선택하신 구성은 **"브리핑 '주목' 종목 → 정량 진입타이밍"** 입니다. 그런데:

- K-Trader에 RSI·ATR·이동평균·MACD·상대강도·거래대금 계산 코드가 **한 줄도 없습니다.** (전체 grep 결과 0건)
- 과거 시세를 가져올 TR(`opt10080` 일봉 / `opt10079` 분봉)도 **연동돼 있지 않습니다.** 엔진이 보는 가격은 실시간 체결 틱뿐이고, 지수 1분봉만 당일 장중에 메모리에 축적합니다(engine.py:2791).
- 백테스터도 CSV를 외부에서 받아야 하며, **그 CSV를 만들 수단이 프로그램 안에 없습니다.**

따라서 "정량 진입타이밍"을 구현하는 방법은 셋뿐이고, 비용이 크게 다릅니다.

### 안 A — 키움 조건검색식을 정량 레이어로 사용 (권장, 즉시 가능)

키움 조건검색식이 곧 정량 스크리너입니다. HTS에서 "20일선 위 + 거래대금 50억 이상 + RSI 50~70" 같은 조건식을 만들어 두면, 엔진이 이미 실시간 편입 이벤트를 받습니다.

구현: **브리핑 후보 목록 ∩ 조건식 편입 종목**. 브리핑이 아침에 후보 리스트를 보내 화이트리스트로 저장 → 조건식이 그 종목을 편입시킬 때만 매수 통과.

- 코드 변경: `_on_real_condition` 게이트 체인에 화이트리스트 검사 1개 추가 (~10줄)
- 장점: 지표 계산·데이터 수집 전부 불필요. 키움이 실시간으로 해줌
- 단점: 조건식 문법의 한계 안에서만 가능. ATR 기반 손절폭 산출은 불가

### 안 B — 클라우드에서 지표 계산 (중간 비용)

클라우드 세션이 pykrx / 네이버금융 등으로 일봉을 받아 RSI·ATR·이동평균·상대강도를 계산하고, **종목코드 + 계산된 손절폭·목표가**까지 담아 신호로 내려보냅니다. 로컬은 실행만 합니다.

- 코드 변경: 신호 스키마 확장 + `condition_params` 동적 주입 (~50줄)
- 장점: 지표 자유도 무제한, 백테스트도 클라우드에서 독립 수행 가능
- 단점: 클라우드↔로컬 신호 채널을 제대로 만들어야 함 (3장 참조)

### 안 C — K-Trader에 지표 모듈 신설 (고비용, 비권장)

`opt10080` 연동 + 지표 계산 + 캐시 DB. 키움 TR 레이트리밋(초당 5회) 때문에 종목당 조회가 느리고, engine.py의 God Class 문제를 더 키웁니다.

## 5. 백테스트 — 쓸 수 없습니다

`src/backtest.py`는 CLI 단독 실행뿐이며 UI/엔진 어디서도 import하지 않습니다. 다음 5가지 낙관 편향이 **모두 같은 방향으로 누적**됩니다.

1. **갭 하락 무시.** 봉 저가가 손절선을 이탈하면 체결가를 `buy_price × (1+loss/100)`으로 **고정**합니다(backtest.py:201~204). 시가 -10% 갭다운도 -1.7% 손절로 기록됩니다. 실전 최대 손실 사건이 구조적으로 삭제됩니다.
2. **터치 = 체결.** 익절은 `bar.high`가 목표가를 스치기만 하면 전량 체결 처리(217~220).
3. **슬리피지 0.** `BacktestConfig`에 항목 자체가 없습니다. 실매매 손절·타임컷은 시장가로 나갑니다.
4. **gross/net 기준 불일치.** 실매매는 수수료·세금 차감 후 순수익률로 판정(`_net_yield`, engine.py:559)하지만 백테스트는 총수익률로 목표가를 잡습니다. **같은 "익절 2.2%"가 실매매에서는 gross 2.44%를 요구**합니다. 백테스트 승률이 구조적으로 높게 나옵니다.
5. **In-sample 과최적화.** `grid_search`가 테스트 기간 전체 결과로 최적값을 고릅니다(347). train/test 분할·walk-forward·거래수 하한·MDD 제약 전부 없음.

추가로, 이 프로그램의 핵심인 **조건식별 파라미터 시스템은 백테스트로 검증 불가능**합니다. `Position.condition` 필드가 선언만 되고 어디서도 채워지지 않습니다(backtest.py:43). 분할매수·분할매도·HARD-STOP·블랙리스트·타임컷도 전부 미구현.

**결론:** 이 백테스트가 흑자를 내는 것은 전략이 유효하다는 증거가 되지 못합니다. 검증은 forward test(페이퍼 또는 소액 실계좌)로만 가능합니다.

## 6. 접목 전 반드시 고쳐야 할 결함

### 6.1 치명 — 제어 흐름이 로그 문자열에 의존

`_last_sell_reason`에 `"손절"`, `"익절"`, `"분할1차"`, `"T.S"`가 들어있는지를 `in` 연산으로 검사해 **호가구분(engine.py:585~594), 매도 재시도 제외(1324), 블랙리스트 모드(3717, 3757), 분할매도 롤백(3360), 쿨다운 스킵(3747)** 을 분기합니다.

→ **이모지나 문구 하나만 바꾸면 매매 로직이 조용히 달라집니다.** AI 신호용 새 매도 사유를 추가할 때 이 함정에 그대로 걸립니다. 열거형(Enum)으로 분리하는 것이 접목 전 1순위 작업입니다.

### 6.2 치명 — 설정 0/False가 삼켜짐

호출부가 대부분 `config.get(...) or 기본값` 패턴입니다(engine.py:3070, 3192~3193). 파이썬에서 `0 or 2.3 == 2.3`이므로 **`profit = 0`(즉시 익절) 설정은 동작하지 않고 2.3%로 대체**됩니다. `ts_use`만 `bool()` 명시 변환으로 방어돼 있고 `loss`/`profit`/`max_rebuy`/`rebuy_cooldown_min`은 무방비입니다.

### 6.3 높음 — `entry_filters`는 죽은 설정

`config_manager.py:212~217`에 `min_volume`, `min_trade_amount`, `max_spread_pct`, `block_upper_limit`이 정의돼 있으나 **engine.py 참조 0건**입니다. 사용자가 "최소 거래대금 50억", "상한가 차단"을 설정해도 **아무 일도 일어나지 않습니다.** 정량 필터를 여기에 붙일 계획이라면 배선부터 해야 합니다.

### 6.4 높음 — 분할매수 2차 이후 리스크 게이트 미검사

`_check_split_buy`(engine.py:3246)는 가용예수금만 확인하고(3290) **`max_hold`·블랙리스트·지수필터·일일손실한도를 재검사하지 않습니다.** 1차 진입 시 통과했으면 이후 단계는 무조건 진행됩니다.

### 6.5 높음 — 신호↔거래 연결이 휴리스틱

`update_trade_result`가 `WHERE stock_code = ? AND result_pnl IS NULL ORDER BY id DESC LIMIT 1`(database.py:788~790)로 결과를 붙입니다. 동일 종목을 다른 신호원으로 동시 보유하거나 분할매수가 켜져 있으면 **엉뚱한 행에 성과가 기록됩니다.** AI 신호의 성과를 측정하겠다는 목적에 직결되는 결함입니다. `trade_features.trade_id`도 선언만 되고 채워지지 않습니다(database.py:167 vs INSERT 751~757).

### 6.6 보안 — 완전 자동 주문으로 가기 전 필수

| 항목 | 현황 |
|---|---|
| IPC 인증 | **없음.** accept 후 무조건 처리(ipc.py:32~34) |
| 계좌 비밀번호 | `REQ_DEPOSIT` args에 `"계좌번호^비밀번호"` **평문**(engine.py:1630~1639) |
| `APPLY_SETTINGS` | 수신 dict를 **무검증으로 설정 전체 교체**(1647~1652). 투자금·손실한도를 통째로 무력화 가능 |
| secrets 암호화 | 키 파생 폴백이 `sha256("username@hostname_ktrader_v6")` — **완전히 결정적**. cryptography 미설치 시 XOR+base64 |
| web_monitor 인증 | 사용자명 미검사, 평문 `!=` 비교, HTTPS 없음. 리버스 프록시 뒤에서는 remote_addr가 항상 127.0.0.1이라 **무인증 전면 개방** |
| replay 방어 | 어떤 채널에도 nonce·타임스탬프 검증 없음 |
| 감사 추적 | 명령 출처(사람/AI/조건식)를 기록하는 필드가 IPC에도 DB에도 없음 |

별개로, **브리핑 트리거 프롬프트에 GitLab PAT(`glpat-...`)와 텔레그램 봇 토큰이 평문으로 저장돼 있습니다.** 트리거 목록 조회 권한만 있으면 그대로 노출됩니다.

### 6.7 중간 — 상태가 22개 병렬 dict로 분산

한 종목의 상태가 `portfolio`, `_pending_buy`, `_pending_sell_qty`, `_pending_order_locks`, `unexecuted_orders`, `_sell_req_ts`, `_last_hard_stop_ts`, `_last_sell_ts`, `_loss_count`, `blacklist`, `_bl_cache`, `_bl_tags`, `_bl_conditions` 등에 흩어져 있고, 종목 종료 시 손으로 하나씩 pop합니다. 그런데 **pop 목록이 세 군데(engine.py:3836, 2432, 1902)에서 서로 다릅니다.** 누락 하나가 유령 상태 또는 메모리 누수입니다.

`locked_deposit`을 누적 카운터에서 재계산 property로 바꾼 것(696~740)은 올바른 처방인데, **나머지 21개 dict에는 적용되지 않았습니다.**

### 6.8 참고 — 테스트와 문서

- 테스트는 `tests/` 아래 7개 존재하나 SM 쿨다운·타임컷·틱 로그에 국한. 매수 게이트 체인, 예수금 SSOT, 체결 처리에 대한 테스트는 없습니다.
- `__init__`(engine.py:154)이 생성만으로 DB·설정·시크릿·COM·소켓·타이머·로그인을 전부 수행 → **엔진을 격리 생성해 테스트하는 것이 불가능**합니다.
- `CLAUDE.md`의 DB 경로(`data/trades.db`)와 설정 경로(`config/settings.json`)는 **코드와 불일치**합니다. 실제는 `%LOCALAPPDATA%\K-Trader\`.
- CHANGELOG는 v10.6(2026-03-22)에서 멈췄고 코드는 v11까지 가 있습니다. engine.py 헤더 주석 140줄 중 상당수가 **이미 삭제된 기능(SmartMoney)** 설명입니다.

## 9. 선결 질문

1. **정량 레이어를 어느 안으로 갈 것인가** (4장 A/B/C). 이것이 이후 모든 작업량을 결정합니다.
2. **모의투자 계좌를 쓸 수 있는가.** 키움 모의투자는 조건검색식을 지원하지 않는 제약이 있어, 단계 5 검증 방법이 달라집니다.
3. **손절/목표가를 누가 정하는가.** 브리핑의 '틀리는 조건'을 청산 트리거로 쓸 것인지, 아니면 K-Trader의 고정 %/ATR 규칙만 쓸 것인지.
4. **기존 조건식 매매와 병행할 것인가, 대체할 것인가.** 병행이면 `max_hold` 배분 규칙과 `condition_priority` 설계가 필요합니다.
