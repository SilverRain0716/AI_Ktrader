# 컨텍스트 팩 빌더 설계 (Phase 3)

- 상태: 확정 · 구현 완료 (`decision/`)
- 날짜: 2026-08-21
- 관련: [설계안 v1](00-design-v1.md) 4.2절 · [ADR 0003](adr/0003-ai-decides-last.md) · `schemas/context_pack.schema.json`

---

## 0. 이 조각이 하는 일

데이터 계층(지표·수급·공시)과 브리핑 계층(관점)을 조인해 **AI 판단 엔진의 단일 입력**을 만든다.

```
market.db ──┐
            ├─→ 컨텍스트 팩 빌더 ─→ context_pack.json ─→ AI 판단 ─→ 결정 JSON
계좌·포지션 ─┘         (여기)
```

설계 원칙은 [ADR 0003](adr/0003-ai-decides-last.md)에서 이미 정했다. 다시 적으면:

> **AI는 컨텍스트 팩 밖의 상태를 알지 못한다.** 여기 없는 정보는 판단에 반영되지 않는다.
> 따라서 컨텍스트 팩 스키마가 곧 AI의 세계다.

이 문서는 그 세계를 **무엇으로 채울 것인가**를 정한다.

---

## 1. 가장 큰 문제 — 유니버스를 어떻게 줄일 것인가

상장 종목이 2,872개다. 전부 넣을 수 없다. **무엇을 넣을지 정하는 규칙이 이 시스템에서 가장 중요한 설계 결정이다** — AI는 유니버스 밖의 종목을 신규 진입 대상으로 고를 수 없기 때문이다(환각 방지 장치이자, 동시에 시야의 한계).

### 1.1 2단계 축소

**1단계 — 하드 필터 (통과 못하면 무조건 제외)**

거래 자체가 불가능하거나 슬리피지가 전략을 삼키는 종목을 먼저 잘라낸다.

| 조건 | 기준 | 근거 |
|---|---|---|
| 거래 가능 | 관리종목·투자위험·정리매매·거래정지 아님 | 주문이 나가지 않거나 나가도 못 빠져나온다 |
| 상장폐지 이력 없음 | `delisting` 테이블에 없음 | 생존편향 방지의 반대편 — 실시간에서도 배제 |
| 유동성 | 20일 평균 거래대금 ≥ **100억원** | 이보다 얇으면 슬리피지가 기대수익을 넘는다 |
| 규모 | 시가총액 ≥ **3,000억원** | 품절주·작전주 배제 |
| 종목 성격 | 우선주·스팩·리츠 제외 | `listing.is_preferred`, `is_spac` |
| 지표 계산 가능 | 유효봉 ≥ **120** | `MIN_BARS_FOR_INDICATORS`. 미달이면 지표가 전부 null |
| 당일 상한가 아님 | 종가 < 상한가 | 진입 자체가 불가능 |

`거래 가능` 판정에 필요한 관리종목·투자경고 목록은 **현재 데이터 계층에 없다.** FDR의 `KRX-ADMINISTRATIVE`는 깨져 있고(조사 결과), KIND는 해외 IP에서 403이었다. 임시로 아래 두 가지로 대체한다.

- 최근 20거래일 내 `halted=1` 행이 있으면 제외 (거래정지 흔적)
- DART 공시에 `상장폐지`·`불성실공시` 카테고리가 있으면 제외

이건 **불완전한 대체재**다. `docs/phase0-verification.md`에 관리종목 목록 확보를 항목으로 추가한다.

**2단계 — 3채널 랭킹 (하드 필터 통과분에서 선별)**

여기가 핵심이다. **단일 점수로 정렬하면 안 된다.** 하나의 스코어로 줄을 세우면 그 스코어가 좋아하는 한 가지 성격의 종목만 상위를 채우고, AI는 서로 다른 근거를 비교할 기회를 잃는다.

성격이 다른 3개 채널에서 각각 뽑아 합집합을 만든다.

| 채널 | 정원 | 선별 기준 | 이 채널이 잡는 것 |
|---|---|---|---|
| **브리핑** | 20 | 최근 3거래일 브리핑에서 `주목` 또는 `조건부` 관점을 받은 종목. 확신도 `상`>`중상`>`중` 순, 같으면 최신순 | 서사·촉매가 확인된 종목 |
| **모멘텀** | 20 | `ma_aligned=true` AND `50 ≤ rsi14 ≤ 70` 인 종목을 `rs20` 내림차순 | 시장 대비 강한 추세 |
| **수급** | 20 | `foreign_net_days ≥ 3` OR `inst_net_days ≥ 3` 인 종목을 (5일 순매수 ÷ 시가총액) 내림차순 | 서사보다 앞서는 자금 흐름 |

- 중복 제거 후 합집합. **상한 60종목.**
- 보유 종목은 채널과 무관하게 `positions`에 들어가므로 유니버스 정원을 소모하지 않는다.
- 각 종목의 `screen_reasons`에 **어느 채널로 들어왔는지** 기록한다. AI가 "이건 수급으로 올라온 종목이고 브리핑 근거는 없다"를 구분할 수 있어야 한다.
- `condition_search_hits`는 키움 조건식 연동 전까지 빈 배열.

### 1.2 브리핑 채널이 만드는 편향 — 명시해 둘 것

브리핑은 "이미 오른 종목"을 사후 설명하는 구조다(상승률·거래대금 상위에서 선정). 브리핑 채널만 두면 추격매수 편향이 그대로 들어온다. 모멘텀·수급 채널을 나란히 두는 이유가 이것이고, **AI 프롬프트에도 이 사실을 명시**한다 — "브리핑 채널 종목은 이미 상승한 뒤 선정된 것이다".

## 2. 토큰 예산

컨텍스트 팩이 커지면 비용과 지연이 오르고, 무엇보다 **AI의 주의가 분산된다.** 상한을 설계에 박는다.

| 블록 | 항목 수 | 항목당 | 소계 |
|---|---|---|---|
| universe (지표+수급+사유) | 60 | ~70 | 4,200 |
| positions | ~8 | ~120 | 960 |
| briefings (요약+관점) | 관점 ~40 | ~110 | 4,400 |
| market·account·constraints·data_quality | — | — | ~600 |
| recent_decisions | 20 | ~40 | 800 |
| **합계** | | | **~11,000 토큰** |

여유가 있다. 상한은 `MAX_PACK_TOKENS = 25000`으로 두고, 초과하면 **채널 정원을 균등 축소**한다(브리핑만 자르면 편향이 생긴다). 추정은 문자 수 ÷ 2.5로 근사한다 — 한국어는 토큰 밀도가 높다.

## 3. 브리핑 선택 규칙과 스키마 수정

### 3.1 스키마 수정이 필요하다

현재 `context_pack.schema.json`의 `briefings.items`는 `briefing.schema.json`을 통째로 `$ref`한다. 그러면 **`sections`(원문 전문)까지 딸려 들어간다.** 브리핑 하나가 4~8KB이고 6종이면 팩 하나에 수만 토큰이 원문으로 들어간다.

→ **컨텍스트 팩에는 요약본만 넣는다.** 인라인 축약 형태로 교체한다.

```
briefings[]:
  briefing_id, kind, published_at, market
  summary            한 줄 요약
  is_fresh           이번 사이클에 새로 나온 브리핑인가
  views[]            관점 블록 (code/symbol/name/stance/confidence/
                     catalyst/reasons/invalidation/check_at)
  parse_warnings     결손 신호
```

`sections`·`raw`·`sources`는 **DB에만 둔다.** AI가 원문을 봐야 하는 상황이면 그때 별도 조회한다.

### 3.2 사이클별 유효 브리핑

| 사이클 | 시각 | 이 사이클에 새로 반영되는 브리핑 |
|---|---|---|
| premarket | 08:20 | 전일 18:00 kr-close-deep · 당일 05:00 us-close · 당일 08:00 kr-premarket-deep |
| midday | 12:20 | 당일 12:00 daily-economy |
| preclose | 15:00 | 당일 14:50 kr-preclose |
| postmarket | 18:30 | 당일 18:00 kr-close-deep |
| event | 수시 | 없음 (직전 사이클 것 유지) |

포함 규칙: `published_at ≤ 생성시각` 이고 `생성시각 − published_at ≤ 36시간`.

**`is_fresh` 플래그가 중요하다.** AI가 "무엇이 새 정보이고 무엇이 이미 본 것인지" 알아야 같은 판단을 반복하거나, 반대로 낡은 근거를 새것처럼 취급하는 일이 없다.

### 3.3 관점의 종목 매칭

브리핑 관점은 `code`가 null인 경우가 있다(실측: 한국 148건 중 53건). `briefing.pipeline map-codes`로 채우되, 끝내 매핑 실패한 관점은 **버리지 않고 `code: null`로 포함**한다. 다만 유니버스 브리핑 채널 선별에는 쓸 수 없다(종목을 특정할 수 없으므로). 그 사실을 `data_quality.warnings`에 남긴다.

## 4. 포지션 — `paper_positions` 테이블 신설

실행 계층이 아직 없다. Phase 5 페이퍼 테스트가 포지션을 만들어야 하고, 컨텍스트 팩은 그걸 읽어야 한다.

```
paper_positions
  position_id        TEXT PK
  code, name
  qty, avg_price
  opened_at, closed_at            (closed_at IS NULL = 보유 중)
  entry_decision_id               이 포지션을 만든 결정
  entry_thesis                    진입 근거 — 보유 판단의 핵심
  invalidation                    진입 시 설정한 무효화 조건
  invalidation_hit                실행 계층이 감시하다 충족되면 1
  stop_price, target_price, max_hold_days
  exit_reason, realized_pnl_krw   청산 후 기록
```

컨텍스트 팩은 열린 포지션을 읽고 `current_price`·`net_yield_pct`·`held_days`·`weight_pct`·`high_since_entry`를 **매번 재계산**한다. 누적 카운터를 두지 않는 원칙(K-Trader에서 얻은 교훈)을 그대로 적용한다.

`net_yield_pct`는 **수수료·거래세 차감 후 순수익률**이다. 총수익률과 섞으면 익절 기준이 조용히 어긋난다 — K-Trader 백테스트가 정확히 이 문제로 승률이 부풀려져 있었다.

## 5. constraints — 저장소에 커밋하지 않는다

운용 자금 규모와 리스크 한도는 [ADR 0004](adr/0004-repo-visibility.md)에 따라 **환경변수로만** 주입한다.

```
AIK_MAX_POSITIONS=8
AIK_MAX_NEW_ENTRIES_PER_CYCLE=2
AIK_MAX_WEIGHT_PCT_PER_NAME=12
AIK_MAX_WEIGHT_PCT_PER_SECTOR=30
AIK_MAX_RISK_PCT_PER_TRADE=0.5      # 1회 최대 손실 (계좌 대비 %)
AIK_DAILY_LOSS_LIMIT_KRW=
AIK_MAX_ORDER_VS_ADV_PCT=3          # 주문금액 / 20일 평균거래대금
```

위 숫자는 **논의를 위한 초안**이지 확정이 아니다. `max_risk_pct_per_trade = 0.5%`는 8종목 동시 보유 시 최대 4% 손실을 뜻한다.

`blocked_codes`는 당일 손절한 종목을 담는다. 실행 계층이 채우며, 그 전까지는 빈 배열.

## 6. data_quality — 언제 멈출 것인가

두 단계로 나눈다.

**(a) 팩 생성 거부** — 예외를 던지고 AI를 호출하지 않는다.

| 조건 | 이유 |
|---|---|
| 일봉 최신일이 직전 거래일보다 **2일 이상** 낡음 | 낡은 가격으로 판단하면 안 된다 |
| 유니버스가 **5종목 미만** | 스크리닝이 깨진 것이지 시장에 후보가 없는 게 아니다 |
| `listing` 테이블 비어 있음 | 데이터 계층이 한 번도 돌지 않았다 |

**(b) 경고 기록** — 팩은 만들되 `data_quality.warnings`에 남긴다.

- 수급 데이터가 1일 이상 낡음
- 해당 사이클의 필수 브리핑 결손
- 브리핑 `parse_warnings` 누적 건수가 임계 초과
- 코드 매핑 실패한 관점 존재

AI 프롬프트는 **"`data_quality.warnings`가 비어 있지 않으면 확신도를 낮추고, 심각하면 `abstain`하라"**를 명시적으로 지시한다. 판단을 규칙으로 막지 않고 AI에게 정보로 준다 — [ADR 0003](adr/0003-ai-decides-last.md)의 원칙이다.

## 7. 재현성과 감사

- `pack_id = {YYYYMMDD}-{HHMM}-{cycle}` (event는 뒤에 4자리 해시)
- 생성된 팩 **전문을 `context_packs` 테이블에 JSON으로 저장**한다.
- 결정 JSON은 `pack_id`를 참조한다. 나중에 "왜 그때 그렇게 판단했는가"를 물으면 **그 시점의 입력 전체를 그대로 복원**할 수 있어야 한다.
- 조립 직후 `jsonschema`로 `context_pack.schema.json` 검증. **통과하지 못한 팩은 AI에 보내지 않는다** — 부분 파싱하지 않는 원칙과 같다.

## 8. 모듈 구조

```
decision/
  __init__.py
  config.py       상한·임계값·채널 정원·환경변수 로딩
  universe.py     하드 필터 + 3채널 랭킹
  positions.py    paper_positions 읽기/쓰기, 파생값 재계산
  pack.py         팩 조립 + 스키마 검증 + 토큰 추정
  pipeline.py     CLI
```

```
python -m decision.pipeline build --cycle premarket
python -m decision.pipeline build --cycle event --code 005930 --trigger invalidation_hit
python -m decision.pipeline show  --pack-id 20260821-0820-premarket
python -m decision.pipeline status
```

테스트는 **고정 시드 DB**를 만들어 결정론적으로 검증한다. 같은 입력 → 같은 팩. 유니버스 선별이 흔들리면 그 자체가 버그다.

## 9. 이 설계가 감수하는 것

- **유니버스 60종목은 시야의 한계다.** 61번째 종목이 그날 최선이었어도 AI는 볼 수 없다. 채널을 셋으로 나눈 것이 이 한계를 완화하는 장치이지 제거하는 장치는 아니다.
- **관리종목·투자경고 목록이 없다.** 대체재(거래정지 흔적·DART 공시)는 불완전하다. Phase 0 항목으로 남긴다.
- **`recent_decisions`는 당분간 비어 있다.** 결정 이력이 쌓여야 채워진다. 첫 몇 주는 AI가 자기 과거 판단을 참조하지 못한다.
- **섹터 정보의 품질이 검증되지 않았다.** `listing.sector`는 FDR 값이고 `max_weight_pct_per_sector` 판정이 여기 의존한다. 실제 데이터를 본 뒤 재검토한다.

## 10. 확정된 값

| 항목 | 값 | 비고 |
|---|---|---|
| 유니버스 상한 | 60 (브리핑 20 / 모멘텀 20 / 수급 20) | |
| 거래대금 하한 | 100억원 | 초안(50억)보다 보수적으로 확정 |
| 시가총액 하한 | 3,000억원 | 초안(1,000억)보다 보수적으로 확정 |
| `paper_positions` | 이번 단계에서 구현 | '보유 중 판단' 경로를 검증하기 위해 |
| 리스크 한도 | 초안값 유지 (8종목 / 12% / 0.5%) | 환경변수. 저장소에 값을 남기지 않는다 |

**임계값을 높인 대가:** 코스닥 중소형주가 거의 빠진다. 하드 필터 통과 종목이 150개 미만이면
3채널 랭킹이 사실상 전수 통과가 되어 의미를 잃으므로, `universe.build()` 가 그 경우 경고를 남긴다
(`RANKING_MEANINGFUL_THRESHOLD`). 실제 데이터 적재 후 통과 종목 수를 세어 재검토한다.

## 11. 구현하면서 드러난 것

설계 문서만으로는 잡히지 않았고 코드와 테스트를 쓰는 과정에서 발견한 것들이다.

### 11.1 `is_fresh` 판정 버그 — 설계가 틀렸다

초안은 "이번 사이클에 새로 나온 브리핑"을 **당일 여부**로 판정하려 했다. 그런데
premarket(08:20)에서 새 정보인 `kr-close-deep` 은 **전일 18:00** 발행이다. 당일로 조건을 걸면
이 브리핑은 영원히 `is_fresh=false` 가 되고, AI는 가장 중요한 새 정보를 "이미 본 것"으로 취급한다.

→ 판정 기준을 **"직전 판단 이후에 나왔는가"**(`FRESH_WINDOW_HOURS = 24`)로 바꿨다.
회귀 테스트 `test_is_fresh_는_전일_18시_브리핑도_잡는다` 로 고정했다.

### 11.2 신선도 검사 순서

초안은 유니버스를 구축한 **뒤** 데이터 신선도를 검사했다. 낡은 가격으로 스크리닝하면 결과 전체가
무의미하므로, `refuse_if_stale()` 을 분리해 **아무 작업도 하기 전에** 호출한다.

### 11.3 스키마가 현실을 반영하지 못한 곳 3건

- `data_quality.flows_as_of` — 수급을 아직 한 번도 적재하지 않으면 null이다
- `positions.entry_decision_id` 등 — 결정 없이 수동으로 연 포지션이 있을 수 있다
- `briefings` 의 `$ref` — 전체 브리핑 스키마를 참조해 `sections`(원문)까지 딸려 들어갔다 (3.1절)

셋 다 **팩이 스키마 검증에서 거부되는 형태**로 드러났다. 검증을 조립 마지막에 강제로 둔 설계가
제 역할을 한 셈이다.
