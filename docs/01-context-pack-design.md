# 컨텍스트 팩 빌더 설계 (Phase 3)

- 상태: 확정 · 구현 완료 (`decision/`)
- 날짜: 2026-08-21
- 관련: [설계안 v1](00-design-v1.md) 4.2절 · [ADR 0003](adr/0003-ai-decides-last.md) · `schemas/context_pack.schema.json`

---

## 0. 이 조각이 하는 일

데이터 계층(지표·수급·공시)과 브리핑 계층(관점)을 조인해 **AI 판단 엔진의 단일 입력**을 만든다.

```
market.db ──┐
            ├─→ 컨텍스트 팩 빌더 ─→ context_pack.json ─→ AI 판단 ─→ 결정 JSON
계좌·포지션 ─┘         (여기)
```

설계 원칙은 [ADR 0003](adr/0003-ai-decides-last.md)에서 이미 정했다. 다시 적으면:

> **AI는 컨텍스트 팩 밖의 상태를 알지 못한다.** 여기 없는 정보는 판단에 반영되지 않는다.
> 따라서 컨텍스트 팩 스키마가 곧 AI의 세계다.

이 문서는 그 세계를 **무엇으로 채울 것인가**를 정한다.

---

## 1. 가장 큰 문제 — 유니버스를 어떻게 줄일 것인가

상장 종목이 2,872개다. 전부 넣을 수 없다. **무엇을 넣을지 정하는 규칙이 이 시스템에서 가장 중요한 설계 결정이다** — AI는 유니버스 밖의 종목을 신규 진입 대상으로 고를 수 없기 때문이다(환각 방지 장치이자, 동시에 시야의 한계).

### 1.1 2단계 축소

**1단계 — 하드 필터 (통과 못하면 무조건 제외)**

거래 자체가 불가능하거나 슬리피지가 전략을 삼키는 종목을 먼저 잘라낸다.

| 조건 | 기준 | 근거 |
|---|---|---|
| 거래 가능 | 관리종목·투자위험·정리매매·거래정지 아님 | 주문이 나가지 않거나 나가도 못 빠져나온다 |
| 상장폐지 이력 없음 | `delisting` 테이블에 없음 | 생존편향 방지의 반대편 — 실시간에서도 배제 |
| 유동성 | 20일 평균 거래대금 ≥ **100억원** | 이보다 얇으면 슬리피지가 기대수익을 넘는다 |
| 규모 | 시가총액 ≥ **3,000억원** | 품절주·작전주 배제 |
| 종목 성격 | 우선주·스팩·리츠 제외 | `listing.is_preferred`, `is_spac` |
| 지표 계산 가능 | 유효봉 ≥ **120** | `MIN_BARS_FOR_INDICATORS`. 미달이면 지표가 전부 null |
| 당일 상한가 아님 | 종가 < 상한가 | 진입 자체가 불가능 |

`거래 가능` 판정에 필요한 관리종목·투자경고 목록은 **현재 데이터 계층에 없다.** FDR의 `KRX-ADMINISTRATIVE`는 깨져 있고(조사 결과), KIND는 해외 IP에서 403이었다. 임시로 아래 두 가지로 대체한다.

- 최근 20거래일 내 `halted=1` 행이 있으면 제외 (거래정지 흔적)
- DART 공시에 `상장폐지`·`불성실공시` 카테고리가 있으면 제외

이건 **불완전한 대체재**다. `docs/phase0-verification.md`에 관리종목 목록 확보를 항목으로 추가한다.

**2단계 — 3채널 랭킹 (하드 필터 통과분에서 선별)**

여기가 핵심이다. **단일 점수로 정렬하면 안 된다.** 하나의 스코어로 줄을 세우면 그 스코어가 좋아하는 한 가지 성격의 종목만 상위를 채우고, AI는 서로 다른 근거를 비교할 기회를 잃는다.

성격이 다른 3개 채널에서 각각 뽑아 합집합을 만든다.

| 채널 | 정원 | 선별 기준 | 이 채널이 잡는 것 |
|---|---|---|---|
| **브리핑** | 20 | 최근 3거래일 브리핑에서 `주목` 또는 `조건부` 관점을 받은 종목. 확신도 `상`>`중상`>`중` 순, 같으면 최신순 | 서사·촉매가 확인된 종목 |
| **모멘텀** | 20 | `ma_aligned=true` AND `50 ≤ rsi14 ≤ 70` 인 종목을 `rs20` 내림차순 | 시장 대비 강한 추세 |
| **수급** | 20 | `foreign_net_days ≥ 3` OR `inst_net_days ≥ 3` 인 종목을 (5일 순매수 ÷ 시가총액) 내림차순 | 서사보다 앞서는 자금 흐름 |

- 중복 제거 후 합집합. **상한 60종목.**
- 보유 종목은 채널과 무관하게 `positions`에 들어가므로 유니버스 정원을 소모하지 않는다.
- 각 종목의 `screen_reasons`에 **어느 채널로 들어왔는지** 기록한다. AI가 "이건 수급으로 올라온 종목이고 브리핑 근거는 없다"를 구분할 수 있어야 한다.
- `condition_search_hits`는 키움 조건식 연동 전까지 빈 배열.

### 1.2 브리핑 채널이 만드는 편향 — 명시해 둘 것

브리핑은 "이미 오른 종목"을 사후 설명하는 구조다(상승률·거래대금 상위에서 선정). 브리핑 채널만 두면 추격매수 편향이 그대로 들어온다. 모멘텀·수급 채널을 나란히 두는 이유가 이것이고, **AI 프롬프트에도 이 사실을 명시**한다 — "브리핑 채널 종목은 이미 상승한 뒤 선정된 것이다".

## 2. 토큰 예산

컨텍스트 팩이 커지면 비용과 지연이 오르고, 무엇보다 **AI의 주의가 분산된다.** 상한을 설계에 박는다.

| 블록 | 항목 수 | 항목당 | 소계 |
|---|---|---|---|
| universe (지표+수급+사유) | 60 | ~70 | 4,200 |
| positions | ~8 | ~120 | 960 |
| briefings (요약+관점) | 관점 ~40 | ~110 | 4,400 |
| market·account·constraints·data_quality | — | — | ~600 |
| recent_decisions | 20 | ~40 | 800 |
| **합계** | | | **~11,000 토큰** |

여유가 있다. 상한은 `MAX_PACK_TOKENS = 25000`으로 두고, 초과하면 **채널 정원을 균등 축소**한다(브리핑만 자르면 편향이 생긴다). 추정은 문자 수 ÷ 2.5로 근사한다 — 한국어는 토큰 밀도가 높다.

## 3. 브리핑 선택 규칙과 스키마 수정

### 3.1 스키마 수정이 필요하다

현재 `context_pack.schema.json`의 `briefings.items`는 `briefing.schema.json`을 통째로 `$ref`한다. 그러면 **`sections`(원문 전문)까지 딸려 들어간다.** 브리핑 하나가 4~8KB이고 6종이면 팩 하나에 수만 토큰이 원문으로 들어간다.

→ **컨텍스트 팩에는 요약본만 넣는다.** 인라인 축약 형태로 교체한다.

```
briefings[]:
  briefing_id, kind, published_at, market
  summary            한 줄 요약
  is_fresh           이번 사이클에 새로 나온 브리핑인가
  views[]            관점 블록 (code/symbol/name/stance/confidence/
                     catalyst/reasons/invalidation/check_at)
  parse_warnings     결손 신호
```

`sections`·`raw`·`sources`는 **DB에만 둔다.** AI가 원문을 봐야 하는 상황이면 그때 별도 조회한다.

### 3.2 사이클별 유효 브리핑

| 사이클 | 시각 | 이 사이클에 새로 반영되는 브리핑 |
|---|---|---|
| premarket | 08:20 | 전일 18:00 kr-close-deep · 당일 05:00 us-close · 당일 08:00 kr-premarket-deep |
| midday | 12:20 | 당일 12:00 daily-economy |
| preclose | 15:00 | 당일 14:50 kr-preclose |
| postmarket | 18:30 | 당일 18:00 kr-close-deep |
| event | 수시 | 없음 (직전 사이클 것 유지) |

포함 규칙: `published_at ≤ 생성시각` 이고 `생성시각 − published_at ≤ 36시간`.

**`is_fresh` 플래그가 중요하다.** AI가 "무엇이 새 정보이고 무엇이 이미 본 것인지" 알아야 같은 판단을 반복하거나, 반대로 낡은 근거를 새것처럼 취급하는 일이 없다.

### 3.3 관점의 종목 매칭

브리핑 관점은 `code`가 null인 경우가 있다(실측: 한국 148건 중 53건). `briefing.pipeline map-codes`로 채우되, 끝내 매핑 실패한 관점은 **버리지 않고 `code: null`로 포함**한다. 다만 유니버스 브리핑 채널 선별에는 쓸 수 없다(종목을 특정할 수 없으므로). 그 사실을 `data_quality.warnings`에 남긴다.

## 4. 포지션 — `paper_positions` 테이블 신설

실행 계층이 아직 없다. Phase 5 페이퍼 테스트가 포지션을 만들어야 하고, 컨텍스트 팩은 그걸 읽어야 한다.

```
paper_positions
  position_id        TEXT PK
  code, name
  qty, avg_price
  opened_at, closed_at            (closed_at IS NULL = 보유 중)
  entry_decision_id               이 포지션을 만든 결정
  entry_thesis                    진입 근거 — 보유 판단의 핵심
  invalidation                    진입 시 설정한 무효화 조건
  invalidation_hit                실행 계층이 감시하다 충족되면 1
  stop_price, target_price, max_hold_days
  exit_reason, realized_pnl_krw   청산 후 기록
```

컨텍스트 팩은 열린 포지션을 읽고 `current_price`·`net_yield_pct`·`held_days`·`weight_pct`·`high_since_entry`를 **매번 재계산**한다. 누적 카운터를 두지 않는 원칙(K-Trader에서 얻은 교훈)을 그대로 적용한다.

`net_yield_pct`는 **수수료·거래세 차감 후 순수익률**이다. 총수익률과 섞으면 익절 기준이 조용히 어긋난다 — K-Trader 백테스트가 정확히 이 문제로 승률이 부풀려져 있었다.

## 5. constraints — 저장소에 커밋하지 않는다

운용 자금 규모와 리스크 한도는 [ADR 0004](adr/0004-repo-visibility.md)에 따라 **환경변수로만** 주입한다.

```
AIK_MAX_POSITIONS=                  # 동시 보유 종목 수          (1~20)
AIK_MAX_NEW_ENTRIES_PER_CYCLE=      # 사이클당 신규 진입          (0~10)
AIK_MAX_WEIGHT_PCT_PER_NAME=        # 종목당 비중 상한 %         (0.1~50)
AIK_MAX_WEIGHT_PCT_PER_SECTOR=      # 섹터당 비중 상한 %         (0.1~100)
AIK_MAX_RISK_PCT_PER_TRADE=         # 1회 최대 손실, 계좌 대비 % (0.01~5)
AIK_DAILY_LOSS_LIMIT_KRW=           # 일일 손실 한도, 원          (0~100억)
AIK_MAX_ORDER_VS_ADV_PCT=           # 주문금액 / 20일 평균거래대금 % (0.1~50)
AIK_PAPER_EQUITY_KRW=               # 페이퍼 시드, 원             (100만~1000억)
```

**이 문서에도 값을 적지 않는다.** 한때 여기에 초안 숫자가 적혀 있었는데, `config.py` 에서 지운 뒤에도
문서에는 남아 있었다 — 저장소에 커밋하지 않는다는 규칙은 코드에만 적용되는 것이 아니다.
설정 예시가 필요하면 `.env.example` 을 본다(거기에도 값은 비어 있다).

**기본값은 없다.** 하나라도 비어 있거나, 숫자가 아니거나, 위 범위를 벗어나거나,
항목 간 조합이 모순이면(예: 종목 비중 상한 > 섹터 비중 상한) `RiskLimitError` 로 팩 생성이 거부된다.
`python -m decision.pipeline status` 가 무엇이 잘못됐는지 한 번에 보여주고, 정상이 아니면 종료 코드 3 을 낸다.

`blocked_codes`는 당일 손절한 종목을 담는다. 실행 계층이 채우며, 그 전까지는 빈 배열.

## 6. data_quality — 언제 멈출 것인가

두 단계로 나눈다.

**(a) 팩 생성 거부** — 예외를 던지고 AI를 호출하지 않는다.

| 조건 | 이유 |
|---|---|
| 일봉 최신일이 직전 거래일보다 **2일 이상** 낡음 | 낡은 가격으로 판단하면 안 된다 |
| 유니버스가 **5종목 미만** | 스크리닝이 깨진 것이지 시장에 후보가 없는 게 아니다 |
| `listing` 테이블 비어 있음 | 데이터 계층이 한 번도 돌지 않았다 |

**(b) 경고 기록** — 팩은 만들되 `data_quality.warnings`에 남긴다.

- 수급 데이터가 1일 이상 낡음
- 해당 사이클의 필수 브리핑 결손
- 브리핑 `parse_warnings` 누적 건수가 임계 초과
- 코드 매핑 실패한 관점 존재

AI 프롬프트는 **"`data_quality.warnings`가 비어 있지 않으면 확신도를 낮추고, 심각하면 `abstain`하라"**를 명시적으로 지시한다. 판단을 규칙으로 막지 않고 AI에게 정보로 준다 — [ADR 0003](adr/0003-ai-decides-last.md)의 원칙이다.

## 7. 재현성과 감사

- `pack_id = {YYYYMMDD}-{HHMM}-{cycle}` (event는 뒤에 4자리 해시)
- 생성된 팩 **전문을 `context_packs` 테이블에 JSON으로 저장**한다.
- 결정 JSON은 `pack_id`를 참조한다. 나중에 "왜 그때 그렇게 판단했는가"를 물으면 **그 시점의 입력 전체를 그대로 복원**할 수 있어야 한다.
- 조립 직후 `jsonschema`로 `context_pack.schema.json` 검증. **통과하지 못한 팩은 AI에 보내지 않는다** — 부분 파싱하지 않는 원칙과 같다.

## 8. 모듈 구조

```
decision/
  __init__.py
  config.py       상한·임계값·채널 정원·환경변수 로딩
  universe.py     하드 필터 + 3채널 랭킹
  positions.py    paper_positions 읽기/쓰기, 파생값 재계산
  pack.py         팩 조립 + 스키마 검증 + 토큰 추정
  pipeline.py     CLI
```

```
python -m decision.pipeline build --cycle premarket
python -m decision.pipeline build --cycle event --code 005930 --trigger invalidation_hit
python -m decision.pipeline show  --pack-id 20260821-0820-premarket
python -m decision.pipeline status
```

테스트는 **고정 시드 DB**를 만들어 결정론적으로 검증한다. 같은 입력 → 같은 팩. 유니버스 선별이 흔들리면 그 자체가 버그다.

## 9. 이 설계가 감수하는 것

- **유니버스 60종목은 시야의 한계다.** 61번째 종목이 그날 최선이었어도 AI는 볼 수 없다. 채널을 셋으로 나눈 것이 이 한계를 완화하는 장치이지 제거하는 장치는 아니다.
- **관리종목·투자경고 목록이 없다.** 대체재(거래정지 흔적·DART 공시)는 불완전하다. Phase 0 항목으로 남긴다.
- **`recent_decisions`는 당분간 비어 있다.** 결정 이력이 쌓여야 채워진다. 첫 몇 주는 AI가 자기 과거 판단을 참조하지 못한다.
- **섹터 정보의 품질이 검증되지 않았다.** `listing.sector`는 FDR 값이고 `max_weight_pct_per_sector` 판정이 여기 의존한다. 실제 데이터를 본 뒤 재검토한다.

## 10. 확정된 값

| 항목 | 값 | 비고 |
|---|---|---|
| 유니버스 상한 | 60 (브리핑 20 / 모멘텀 20 / 수급 20) | |
| 거래대금 하한 | 100억원 | 초안(50억)보다 보수적으로 확정 |
| 시가총액 하한 | 3,000억원 | 초안(1,000억)보다 보수적으로 확정 |
| `paper_positions` | 이번 단계에서 구현 | '보유 중 판단' 경로를 검증하기 위해 |
| 리스크 한도 | 초안값 유지 | 환경변수. **저장소에 값을 남기지 않는다** — 이 표에도 적지 않는다 |

**임계값을 높인 대가:** 코스닥 중소형주가 거의 빠진다. 하드 필터 통과 종목이 150개 미만이면
3채널 랭킹이 사실상 전수 통과가 되어 의미를 잃으므로, `universe.build()` 가 그 경우 경고를 남긴다
(`RANKING_MEANINGFUL_THRESHOLD`). 실제 데이터 적재 후 통과 종목 수를 세어 재검토한다.

## 11. 구현하면서 드러난 것

설계 문서만으로는 잡히지 않았고 코드와 테스트를 쓰는 과정에서 발견한 것들이다.

### 11.1 `is_fresh` 판정 버그 — 설계가 틀렸다

초안은 "이번 사이클에 새로 나온 브리핑"을 **당일 여부**로 판정하려 했다. 그런데
premarket(08:20)에서 새 정보인 `kr-close-deep` 은 **전일 18:00** 발행이다. 당일로 조건을 걸면
이 브리핑은 영원히 `is_fresh=false` 가 되고, AI는 가장 중요한 새 정보를 "이미 본 것"으로 취급한다.

→ 판정 기준을 **"직전 판단 이후에 나왔는가"**(`FRESH_WINDOW_HOURS = 24`)로 바꿨다.
회귀 테스트 `test_is_fresh_는_전일_18시_브리핑도_잡는다` 로 고정했다.

### 11.2 신선도 검사 순서

초안은 유니버스를 구축한 **뒤** 데이터 신선도를 검사했다. 낡은 가격으로 스크리닝하면 결과 전체가
무의미하므로, `refuse_if_stale()` 을 분리해 **아무 작업도 하기 전에** 호출한다.

### 11.3 스키마가 현실을 반영하지 못한 곳 3건

- `data_quality.flows_as_of` — 수급을 아직 한 번도 적재하지 않으면 null이다
- `positions.entry_decision_id` 등 — 결정 없이 수동으로 연 포지션이 있을 수 있다
- `briefings` 의 `$ref` — 전체 브리핑 스키마를 참조해 `sections`(원문)까지 딸려 들어갔다 (3.1절)

셋 다 **팩이 스키마 검증에서 거부되는 형태**로 드러났다. 검증을 조립 마지막에 강제로 둔 설계가
제 역할을 한 셈이다.

### 11.4 통과 종목 수를 세는 가드는 아무것도 보장하지 못했다

`RANKING_MEANINGFUL_THRESHOLD = 150` 은 "하드 필터 통과 종목이 너무 적으면 랭킹이 무의미하다"를
잡으라고 둔 값이다. 실측에서 통과 종목은 205개였고, 경고는 뜨지 않았다.

그런데 그 205는 **일봉이 적재된 314종목 위에서 센 숫자**였다. 시총 3,000억을 넘는 후보는
실제로 637종목인데, 배치를 `--limit 300` 으로 돌려 절반이 아예 데이터 없이 빠져 있었다.
클래시스·에스티팜·씨젠·에스엠 같은 1.5~2조 종목이 통째로 없는 상태에서 "상위 60종목"을 뽑고 있었다.

**가드가 맞는 답을 냈지만 이유가 틀렸다.** 이 종류가 제일 위험하다 — 앞으로도 계속 침묵할 것이므로.

세 군데를 고쳤다.

1. **적재 대상을 개수가 아니라 시총 하한으로 정의한다.**
   `data.config.INGEST_MIN_MARKET_CAP_BIL_KRW` 가 하드 필터의 시총 하한과 **같은 값이어야 한다**는
   등식을 테스트로 고정했다. 이 등식이 커버리지 지표가 의미를 갖는 유일한 근거다.
   `--limit` 는 시험용으로만 남기고, 쓰면 "잘림"을 로그에 남긴다.

2. **커버리지를 측정한다.** 모집단 = 시총 하한을 넘는 거래 가능 보통주(우선주·스팩·관리종목·
   상장폐지·거래정지 제외), 커버리지 = 그 중 지표까지 확보된 비율.
   전 기간 거래정지 종목을 모집단에서 뺀 이유는, 남겨두면 커버리지가 영원히 100%에 못 미치고
   그 미달분이 무슨 뜻인지 아무도 기억하지 못하게 되기 때문이다 — **이유를 잊은 채 통과하는
   임계값이 애초에 이 결함의 정체였다.**

3. **모수가 깨지면 멈춘다.** `check_coverage()` 를 `refuse_if_stale()` 바로 뒤,
   유니버스 구축 **앞**에 둔다. 95% 미만이면 `data_quality` 에 경고, 70% 미만이면 팩 생성을 거부한다.
   커버리지 값 자체(`universe_coverage`)도 팩에 실어, AI가 자기 시야가 얼마나 좁은지 알고
   abstain 을 판단할 수 있게 했다.

**실측 결과:** 637종목 적재(일봉 실패 0 / 수급 실패 0) → 커버리지 100%(모집단 632, 거래정지 2종목 제외),
하드 필터 통과 205 → **242**, 유니버스에 그동안 보이지 않던 9종목이 새로 들어왔다.

**교훈은 앞 장의 한 겹 위다.** 시드 DB는 로직을, 실데이터는 전제를 검증한다.
그런데 **실데이터 테스트조차 "데이터가 얼마나 들어왔는가"는 검증하지 않는다.**
118건 통과·린트 통과·스키마 통과·팩 생성 성공 — 모든 신호가 초록인데 모집단의 절반이 비어 있었다.
가드는 값을 검사할 게 아니라 **그 값이 나온 모수를 검사해야 한다.**

### 11.5 켜지지 않은 필터는 고장 여부를 알 수 없다

하드 필터에는 처음부터 악재공시 배제 분기가 있었다.

```sql
AND l.code NOT IN (SELECT DISTINCT code FROM disclosures
                   WHERE category IN ('상장폐지','불성실공시'))
```

그런데 `disclosures` 테이블이 **0건**이었다. DART 적재를 한 번도 돌리지 않았기 때문이다.
조건은 항상 참이었고, 아무것도 걸러내지 않았다. 코드는 있는데 효력이 없는 상태다.

적재를 켜자마자 두 가지가 드러났다.

**하나 — 카테고리는 "주제"이지 "방향"이 아니다.**
`상장폐지`·`불성실공시` 로 분류된 공시 안에 **해소를 알리는 것**이 섞여 있다.
실측 10일치에서 나온 것들:

| 공시명 | 실제 의미 |
|---|---|
| `불성실공시법인**미**지정 (지정유예)` | 지정하지 **않았다** |
| `기타시장안내 (상장적격성 실질심사 **대상 제외 결정**)` | 심사 대상에서 **빠졌다** |
| `주권매매거래정지**해제** (… 대상 제외 결정)` | 정지가 **풀렸다** |
| `기타시장안내 (… 대상결정 **기한 안내**)` | 아직 결정이 **안 났다** |
| `기타시장안내 (… 절차 **미진행**)` | 절차를 밟지 **않았다** |
| `불성실공시법인지정**예고**` | 확정되면 `지정` 공시가 따로 난다 |

카테고리만 보고 배제하면 이 여섯이 전부 악재로 뒤집힌다. 배제가 **영구**이므로
오탐 한 건이 종목을 영원히 배제한다 — 되돌아올 길이 없는 판정에는 방향까지 봐야 한다.
→ `dart.is_disqualifying()` 이 확정된 악재만 True 로 둔다. 15건이 재판정으로 살아났다.

**둘 — "영구"는 "해소 공시를 무시한다"는 뜻이 아니다.**
덱스터는 `상장적격성 실질심사 대상 제외 결정` + `주권매매거래정지해제` 로 완전히 풀렸는데,
과거의 사유 발생 공시 한 건만 남아 있으면 영원히 배제된다. 그건 정책이 아니라 버그다.
→ `dart.is_resolving()` 을 따로 두고, 종목별 **마지막 배제 공시 > 마지막 해소 공시**일 때만 배제한다.
"아직 아니다"(예고·기한 안내·미진행)는 중립이라 배제도 해제도 하지 않는다.

**셋 — 배제 집합의 크기는 적재 기간에 정비례한다.**
기간 제한이 없으므로, 공시를 6개월치 적재하면 6개월치만큼, 3년치 적재하면 3년치만큼 배제된다.
같은 코드가 적재 이력에 따라 다르게 동작한다. 이걸 숨기면 "이 종목은 왜 유니버스에 없나"에
답할 수 없으므로, `data_quality.disclosures_since` 로 팩에 적재 시작일을 싣는다.

**실측 결과 (2026-06-24 ~ 08-21, 공시 23,196건):**
배제 52종목, 그 중 유니버스 모집단(3,000억+)에 드는 것은 4종목
(삼립·제주은행·파라다이스·케어젠 — 전부 실제 `불성실공시법인지정`).
넷 다 **이미 거래대금 하한(100억)에서 걸려 있었으므로 하드 필터 통과 수는 242로 변함이 없다.**
지금 시점에 이 필터는 유니버스를 바꾸지 않는다. 적재 기간이 길어지면 달라진다.

**결함 1·2와 같은 구조다.** CI는 테스트를 돌리지 않았고, 커버리지 가드는 절단된 모수를 셌고,
공시 필터는 빈 테이블을 조회했다. 셋 다 **초록불이었다.**
동작하지 않는 것과 동작해서 통과하는 것은 겉으로 구분되지 않는다.

### 11.6 라벨이 없다고 근거가 없는 것은 아니다

점검에서 "관점 208건 중 40%가 근거 2개 미만"으로 집계됐다. 특히 `kr-preclose` 는
**41건 전부** 근거 0개였다. 처음 진단은 "브리핑 포맷에 근거 필드가 구조적으로 없다,
브리핑 생성 프롬프트를 고쳐야 한다" 였다. **틀렸다.**

원문을 열어 보면 근거는 있다. 별도 `근거:` 라벨을 쓰지 않고 종목명 뒤 서술문에 담겨 있을 뿐이다.

```
1. SK하이닉스(000660) +3%대 — 40조 자사주 취득·소각 매 거래일 실매입(승계)
   +간밤 SOX +0.53%·마이크론 강세. 단 오늘 조회공시요구 접수, 내용 미확정.
관점: 조건부 / 확신도 중 / 틀리는 조건: … / 확인: …
```

`parse_header()` 는 `—` 를 기준으로 **왼쪽만** 취해 종목명·코드를 뽑고 오른쪽을 버렸다.
버려진 쪽에 근거가 있었다. 파서 문제를 브리핑 품질 문제로 오진한 것이다.

**분리 규칙.** `+` 는 근거를 잇는 접속어이면서 등락률 부호이기도 하다(`간밤 SOX +0.53%`).
뒤에 숫자가 오면 부호이므로 자르지 않는다. 쉼표도 마찬가지로 자릿점(`+3,440억`)을 보호한다.

**세지 않는 것.** `프리마켓 +9.46%` 는 종목이 움직였다는 사실일 뿐 왜 움직였는지가 아니다.
`DART 당일 공시 없음` 은 촉매의 **부재**를 알리는 꼬리말이지 상승 근거가 아니다.
이걸 근거로 세면 경고만 사라지고 입력 품질은 그대로다 — 가드가 틀린 이유로 통과하는 그 패턴이다.

**결과**

| | 이전 | 이후 |
|---|---|---|
| 근거 0개 | 57 | **6** |
| 근거 2개 이상 | 125 | **165** |
| 규칙 미달 | 83 (40%) | **43 (21%)** |
| kr-preclose 미달 | 41 | **8** |
| us-premarket 미달 | 38 | 31 |

**진단이 정반대로 뒤집혔다.** `kr-preclose` 미달은 파서 문제였고 대부분 해소됐다.
남은 `us-premarket` 31건은 진짜로 내용이 얇다 — `로켓랩(RKLB) — 프리마켓 +9.46%` 처럼
근거 없이 등락률만 적힌 항목이다. **프롬프트를 고쳐야 할 곳은 14:50 이 아니라 21:30 이다.**

### 11.7 파생값은 규칙이 바뀌면 낡는다

`parse_warnings` 는 파싱 시점에 기록되는데, 코드 매핑은 그 뒤에 따로 돈다.
걷어내지 않으면 이미 해결된 경고가 영원히 남는다 — `종목코드 없음` 이 **38건**으로
집계됐지만 실제 미매핑은 **2건**(LS전기, 삼성생명·보험주)이었다.
경고 통계가 실제보다 나쁘게 보이고, `MAX_PARSE_WARNINGS` 임계 판정까지 함께 왜곡된다.

같은 문제가 근거에도 있다. 파서 규칙이 바뀌면 이미 적재된 관점의 근거·경고가 낡고,
같은 DB 안에 옛 규칙과 새 규칙이 섞인다.

→ `task_map_codes` 는 코드가 채워진 관점의 경고를 걷어낸다.
→ `task_reparse` 는 저장된 원문으로 근거를 다시 판정하고 경고를 실제 개수로 다시 쓴다.
   `sync` 뒤에 자동으로 돌고, 원문 재수집 없이 단독으로도 돌릴 수 있다.

**해결되지 않은 경고까지 지우지 않는다.** 매핑에 실패하면 경고는 남고,
근거가 여전히 1개면 `근거 0개` 를 `근거 1개` 로 고쳐 쓴다.
경고를 지우는 게 목적이 아니라 실제 상태를 반영하는 게 목적이다.
`_migrate_v6` 가 이미 적재된 공시를 다시 판정한 것과 같은 원칙이다.

**결과:** 파싱 경고 총 45건 — `근거 1개` 37 / `근거 0개` 6 / `종목코드 없음` 2.
전부 실제 상태와 일치한다.

### 11.8 '기타' 가 크면 섹터 한도는 아무것도 막지 못한다

`sector_group` 의 '기타' 가 500종목(18%)이었다. 처음에는 롱테일 잡음으로 봤는데,
모집단(시총 3,000억 이상)만 추려 보니 **87종목**이 거기 있었다. 무엇이 있었냐면:

| 업종 | 종목 |
|---|---|
| 일차전지 및 이차전지 제조업 | LG에너지솔루션, 삼성SDI, 포스코퓨처엠, 에코프로비엠, 엘앤에프 |
| 기초 의약물질 제조업 | 삼성바이오로직스, 셀트리온, 휴젤, SK바이오사이언스 |
| 기타 식품 제조업 | CJ제일제당, 농심, 오리온, 삼양식품, 오뚜기 |
| 담배 제조업 | KT&G |

**섹터 비중 한도 30% 의 목적은 "같이 움직이는 종목에 몰리지 않는 것"이다.**
그런데 한국 시장에서 상관관계가 가장 높은 테마인 2차전지 5종목을 전부 사도
'기타' 안에서 한 덩어리로 잡히고, 그 버킷에는 사료·학원·여행사도 섞여 있다.
**한도가 정확히 작동해야 할 바로 그 자리에서 작동하지 않는다.**

원인은 키워드가 좁았던 것이다. `의약품` 만 보면 `기초 의약물질 제조업` 이 빠지고,
`식료품` 만 보면 `기타 식품 제조업` 이 빠진다.

**조치.** 키워드를 넓히고 버킷 3종(`2차전지`·`서비스·레저`·`지주·상사`)을 추가했다.
`2차전지` 를 화학이나 전기전자에 넣지 않은 이유는, 넣는 순간 그 버킷의 비중이 부풀어
같은 문제가 한 겹 옮겨갈 뿐이기 때문이다.

**오분류 검증.** 규칙을 넓히면 기존 분류가 새는 것이 더 위험하다.
DB의 **전 업종 158종**에 대해 변경 전후를 전수 대조했다 — 변경 35건은 **전부 `기타` → 실제 업종**이고,
이미 올바르게 분류돼 있던 123종은 **하나도 바뀌지 않았다.**

| | 이전 | 이후 |
|---|---|---|
| 전체 '기타' | 500 (18%) | **194 (7%)** |
| 모집단 '기타' | 87 | **5** |

`_migrate_v7` 이 이미 적재된 행을 다시 분류한다 — `industry` 원문은 그대로 있으므로
재적재 없이 되돌릴 수 있다. 규칙이 바뀌었는데 옛 행을 두면 같은 DB 안에 기준이 두 개가 된다
(11.7·`_migrate_v6` 와 같은 원칙).

**남은 한계.** 두산테스나·네패스아크는 실제로 반도체 테스트 회사인데 KRX 업종분류가
`그외 기타 전문, 과학 및 기술 서비스업` 이다. 업종 문자열만으로는 잡을 수 없다.
모집단에 남은 '기타' 5종목이 이 부류다.

### 11.9 값이 맞는지는 아무도 검사하지 않고 있었다

앞선 점검(11.4~11.8)은 전부 **"데이터가 들어왔는가"** 를 고쳤다.
전면 재점검에서 나온 것은 **"들어온 값이 맞는가"** 다. 더 많고 더 깊었다.

#### 손실이 매수 여력을 늘렸다

```python
cash = total_equity − holdings_value(conn)   # holdings_value 는 현재 평가금
```

| 상황 | 평가금 | 가용 현금 |
|---|---|---|
| 5,000만원 진입 | 50,000,000 | 50,000,000 |
| **-30% 하락** | 35,000,000 | **65,000,000** |
| +30% 상승 | 65,000,000 | 35,000,000 |

**포지션이 깨질수록 쓸 수 있는 돈이 늘어난다.** 물타기를 구조적으로 유도하고,
잘 가는 포지션이 있으면 신규 진입을 막는다. 리스크 관리에서 부호가 정확히 뒤집혔다.
`total_equity` 가 상수라 **실현손실은 계좌에서 사라졌다.**

→ `account_state()` 가 회계 항등식으로 계산한다.
`cash = 시드 − Σ취득원가 + Σ실현손익`, `total_equity = cash + Σ평가금`.
`unrealized_pnl` 도 순액 기준으로 바꿨다 — 같은 블록에 순/총이 섞여 있었다.

#### 유니버스가 미래 브리핑을 읽었다

`pack.py` 의 브리핑 블록은 `published_at <= generated_at` 으로 미래를 막는데,
`universe.py` 의 브리핑 **채널** 쿼리에는 하한만 있었다.

```
08:20 팩 / DB에 당일 18:00 브리핑
  팩의 briefings 블록 : []                          ← 정상 제외
  유니버스 진입 사유   : briefing:kr-close-deep 주목  ← 10시간 뒤 정보
```

**팩에는 없는 브리핑을 근거로 종목이 유니버스에 올랐다.**
실운영에서는 미발행 브리핑이 DB에 없어 대체로 안전하지만,
**다음 단계가 백테스트**다. 리플레이에 이 빌더를 재사용하면 이 채널이 미래수익을 만든다.

같은 이유로 지표·거래정지·공시 쿼리에도 `as_of` 상한을 관통시켰다.
특히 거래정지 룩어헤드는 "나중에 정지될 종목을 미리 피하는" 완벽한 미래 정보였다.

#### KOSPI 관리종목이 하나도 걸러지지 않았다

`is_managed` 는 FDR 소속부(`dept`)로 판정하는데 **소속부는 코스닥에만 있다.**

| 시장 | 종목 | dept 채워짐 | is_managed |
|---|---|---|---|
| KOSDAQ | 1,822 | 1,822 | 161 |
| **KOSPI** | **942** | **0** | **0** |

실측에서 KOSPI 소형주 40종목 중 **18건이 관리종목**이었고 전부 하드 필터를 통과했다.

→ 네이버 `m.stock.naver.com/api/stock/{code}/basic` 의 `isManagement` 를 추가.
**단, 덮어쓰지 않고 합집합으로 쓴다.** 처음에 네이버로 대체했다가
메지온·에스티큐브·서울바이오시스·HLB생명과학 4종목을 잃었다 —
네이버는 관리종목만 잡고 **투자주의환기는 안 잡는다.** 두 신호가 잡는 것이 다르다.

그리고 `is_managed=0` 이 "아니다"와 "판정 못했다"를 겸하고 있었으므로
`is_managed_known` 을 분리했다(스키마 v8). 판정 불가는 팩에 경고로 실린다 —
**실패를 조용히 통과로 만들지 않는다.**

#### 매주 월요일 아침이 거부됐다

`MAX_OHLCV_STALE_DAYS = 2` 가 달력일이었다. 배치는 18:30에 돈다.
금요일 배치 → 월요일 08:20 = 3일 낡음 → **거부.**
매주 월요일의 세 사이클이 통째로 죽고 있었다.

→ 거래일 기준(`MAX_OHLCV_STALE_SESSIONS`)으로 바꿨다.
지수 봉이 휴장일에 없으므로 거래일 달력 노릇을 한다.

#### 지표 이름과 계산이 달랐다

| 지표 | 문제 | 이후 |
|---|---|---|
| `high_52w_gap_pct` | **종가** 최댓값. 장중 고가 2배여도 `0.0` | 장중 고가 기준 `-50.0` |
| | 봉 부족해도 값을 냄 | 200봉 미만이면 `null` |
| `volume_ratio` | 당일을 분모에 포함. 10배가 **6.9배** | `10.0` |
| `*_bil_krw` | 이름은 십억, 값은 억. 삼성전자 시총 `16,457,274` | `*_eok_krw` 로 리네임 |

단위 문제는 **소비자가 LLM 이라서** 치명적이다. 팩에 단위 범례가 없고 스키마는
AI에게 전달되지 않는다. `adv20_bil_krw: 350` 을 "3,500억"으로 읽으면 유동성 판단이 10배 틀린다.
`execution/` 이 비어 있는 지금이 고칠 마지막 시점이었다.

#### 하드코딩된 안전장치

`blocked_codes`(당일 손절 재진입 금지)와 `daily_loss_limit_hit` 이 빈 값·False 상수였다.
아침에 손절한 종목을 점심에 다시 사도 아무것도 막지 않았고,
`daily_loss_limit_krw` 를 환경변수로 정성껏 주입해도 효과가 없었다. 둘 다 실제 값으로 채웠다.

#### 남은 것

`recent_decisions` 는 여전히 빈 배열이다 — 판단 엔진이 없으므로 채울 것이 없다.
`TRIM`(부분 청산)도 미구현이다. 스키마가 약속한 계약이므로 판단 엔진과 함께 닫아야 한다.

**교훈.** 어제의 커버리지 가드는 "값이 아니라 모수를 보라"였다.
그 원칙을 **종목 수에는 적용하고 시점·단위·회계에는 적용하지 않았다.**
스키마 검증은 형식만 본다. 값의 정합성을 보는 층이 따로 필요하다 —
회계 항등식, `as_of` 상한, 물리적 상한(`|change_pct| ≤ 30%`) 같은 것들.
이번에 나온 결함은 **전부 그런 검사로 자동 검출 가능했다.**
