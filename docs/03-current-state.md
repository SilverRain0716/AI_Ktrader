## 2. 반복해서 드러난 한 가지

이 저장소에서 지금까지 나온 결함은 성격이 대부분 같았다.

> **동작하지 않는 것과 동작해서 통과하는 것은 겉으로 구분되지 않는다.**

- CI 가 테스트를 돌리지 않았다 — 초록불이었다
- 커버리지 가드가 **잘린 모수**를 세었다 — 통과했다
- 공시 필터가 **빈 테이블**을 조회했다 — 조용했다
- 파서가 **근거가 들어 있는 쪽**을 버렸다 — 경고가 없었다
- 섹터 한도가 **'기타' 안에서** 무의미했다 — 한도는 걸려 있었다
- 리스크 한도를 **아무도 설정하지 않은 채** 초안 값으로 돌았다 — 팩은 정상이었다

그래서 이 프로젝트의 작업 규칙이 하나 생겼다.
**고칠 때마다 "그 상태로 되돌아가는 경로"를 실패하는 테스트로 막는다.**
결함 수정 PR 들이 더한 것이 **134건 / 252건(53%)** 이다 (118 → 200 → 216 → 252).

## 4. 순서를 바꿔야 한다

현 로드맵은 `3 백테스트 → 4 판단엔진 → 5 페이퍼 3개월 → 6 실행계층+게이트 → 7 실계좌` 다.
여기에 두 가지 문제가 있다.

- **5를 6보다 먼저 두면 페이퍼가 수동이 된다.** 포지션을 여는 함수는 있으나 부르는 코드가 없다
- **6에서 게이트와 주문이 동시에 태어난다** (R1)

두 문제의 해답이 같다.

> **실행 계층에서 주문만 뺀 것을 먼저 만들고, 3개월 돌린 뒤, 주문 어댑터만 갈아끼운다.**
> 그러면 게이트는 실주문을 만나기 전에 이미 3개월간 검증된 상태가 된다.

| 순서 | 내용 |
|---|---|
| **지금** | ~~앱키 발급~~(08-30 완료) → 모의 계좌 신청(A2) · B1 재측정 · 죽은 설정 정리(R3) · 브리핑 프롬프트 미러링(R6) |
| ~~**1**~~ **(2026-08-30 완료)** | 판단 엔진 + 결정 저장소 + 프롬프트를 한 회차에 만들었다 ([ADR 0007](adr/0007-judgment-engine.md)). 남은 것은 Arm 0 랭킹 규칙 정의 |
| **2** | 검증 게이트 + 페이퍼 집행기. **킬 스위치와 멱등성을 여기서 배선한다** — 주문 코드가 생기기 전에 |
| **3** | 스케줄러 + 알림. 자동화와 관측은 같이 온다 |
| — | *여기까지가 페이퍼 forward test 를 시작할 수 있는 최소 조건이다* |
| **4** | 페이퍼 3개월 · 백테스트 병행(다른 코드이므로 1~3과 병렬 가능) |
| **5** | 주문 어댑터 교체 → 모의투자. 새로 쓰는 것은 주문과 실시간 감시뿐이다 |
| **6** | 소액 실계좌. **F5(규율 미집행)가 통과된 뒤에만.** 한도 상향은 F2·F3 가 판정된 뒤다 — ADR 0006 은 그때까지 이 시스템을 검증되지 않은 상태로 본다 |

### 하지 말아야 할 것

- 백테스트를 건너뛰고 페이퍼 성과를 믿는 것 — 기준선이 없으면 AI 기여분을 분리할 수 없다
- 주문 코드와 게이트를 같은 회차에 쓰는 것 (R1)
- 판단 엔진만 만들고 결정 기록을 미루는 것 — 미룬 기간의 판단은 사후에 재현되지 않는다
- 알림 없이 스케줄러를 붙이는 것 (R5)
- 죽은 설정을 그대로 두는 것 — 지우거나 배선한다. "나중에 연결하겠다"가 가장 위험하다
