# ADR 0007 — 판단은 저장소 안의 봉인된 API 호출로 하고, 무엇을 보고 판단했는지를 바이트 단위로 남긴다

- 상태: 채택
- 날짜: 2026-08-30
- 관련: [ADR 0003](0003-ai-decides-last.md), [ADR 0005](0005-backtest-scope.md), [ADR 0006](0006-edge-hypothesis.md), [설계안 v1](../00-design-v1.md) 7장, [현재 좌표](../03-current-state.md) 3.1 블록 A·B

## 맥락

[설계안 v1](../00-design-v1.md) 7장 2번이 **"AI 모델을 어디서 호출할 것인가"** 를 미결로 남겼다.

> 현재 브리핑 파이프라인처럼 스케줄 세션에서 호출할지, 별도 API 호출 코드를 둘지.

그때는 브리핑 방식밖에 없었으므로 열어 두는 것이 정직했다. 지금은 그 사이에 [ADR 0005](0005-backtest-scope.md)의 3-arm 대응비교와 [ADR 0006](0006-edge-hypothesis.md)의 반증 조건 F1~F5가 채택됐고, **그 둘이 호출 방식에 제약을 건다.** 더 미루면 판단 엔진 코드가 붙은 뒤에 같은 갈림길에 서게 된다.

동시에 확인된 사실이 있다. **`decision.schema.json` 을 참조하는 코드가 저장소 전체에 0건이다.** 142줄짜리 계약에 생산자도 소비자도 없다([03-current-state.md](../03-current-state.md) 3.2). 스키마를 고치는 비용이 0인 마지막 시점이다.

## 결정

> **판단은 도구가 없는 저장소 안 API 호출로 하고, 결정 저장소를 판단 엔진과 같은 회차에 만들며, 각 결정에는 "무엇을 보고 판단했는가"를 재구성이 아니라 저장된 바이트로 남긴다.**

세 갈래로 나눠 적는다.

### 결정 1 — 호출은 저장소 안, 도구 없이

`decision/engine.py` 에 Anthropic SDK 직접 호출 코드를 둔다. 인터페이스는 이 수준으로 제한한다.

```
engine.render_input(pack: dict, arm: int) -> str          # 순수 함수, 결정론적 직렬화
engine.decide(conn, pack: dict, arm: int) -> DecisionRecord  # 호출·검증·재시도·기록
```

### 결정 2 — 3-arm 은 정본 팩 한 벌 + 순수 파생 함수

팩은 현행대로 **브리핑 포함 한 벌만** 만든다. Arm 2 입력은 정본 팩에 `derive_arm2(pack)` 를 적용해 만든다.

`derive_arm2` 가 하는 일:

1. `briefings` 블록 제거
2. `universe` 에서 **briefing 채널로만 들어온 종목 제거** (`channels == ["briefing"]`)
3. 남은 종목의 `screen_reasons`·`channels` 에서 briefing 항목 제거
4. `data_quality` 의 브리핑 관련 경고 제거

Arm 0(정량 랭킹)도 같은 정본 팩을 입력으로 받는 결정론적 함수로 만들고, **출력을 같은 결정 계약**(`decision.schema.json` 인스턴스, `arm=0`)으로 낸다.

### 결정 3 — 결정 저장소는 append-only 이고, 입력 전문을 봉인한다

`decisions` 테이블에 INSERT 만 존재한다. UPDATE·DELETE 경로를 만들지 않고, **그 부재를 테스트로 고정한다.**

| 컬럼 | 무엇 |
|---|---|
| `decision_id` | **러너가 생성**하는 멱등키. `(pack_id, arm)` 당 하나. 재시도는 같은 id 를 재사용한다 |
| `pack_id` · `pack_sha256` | 참조 + 봉인 해시 |
| `arm` · `cycle` · `generated_at` · `valid_until` | 러너가 사이클에서 결정론적으로 채운다 |
| `model` · `prompt_id` · `prompt_sha256` · `api_params` · `render_version` | 판단 함수의 신원 |
| `rendered_input` | **모델에 실제로 보낸 입력 전문(verbatim)** |
| `raw_response` | 모델이 반환한 원문 그대로 — 파싱 전 |
| `payload` | 스키마 검증을 통과한 결정 JSON (실패 시 null) |
| `status` | `ok` / `abstain` / `schema_rejected` / `api_error` / `timeout` / `expired` |
| `attempt` · `request_id` · `usage_tokens` · `latency_ms` | 진단·비용 실측 |

## 근거

### 1. 외부 세션은 F3 를 정의상 오염시킨다

[ADR 0003](0003-ai-decides-last.md) 설계원칙 1은 **"AI 는 팩 밖의 상태를 알지 못한다"** 이다. 그런데 스케줄 세션(Claude Code 류)에는 도구·웹·파일 접근이 있다. 세션 속 모델이 종목을 검색해 보는 순간 그 전제가 깨진다.

깨지는 방식이 조용해서 위험하다. **`Arm 1 − Arm 2` 차이에 "브리핑"이 아니라 "세션이 밖에서 본 것"이 섞인다.** [ADR 0006](0006-edge-hypothesis.md) 의 F3 는 정확히 그 차이를 브리핑의 증분으로 읽는 반증 조건이므로, **F3 는 측정에 실패하는 것이 아니라 틀린 것을 측정하게 된다.** 그리고 그것이 일어났는지 사후에 알 방법이 없다.

도구 없는 messages API 호출은 봉인된 세계를 **구조로** 보장한다. 프롬프트로 "검색하지 마라"라고 부탁하는 것과 다르다.

### 2. 3-arm 은 짝을 원자적으로 기록해야 한다

[ADR 0005](0005-backtest-scope.md) 3-arm 절은 **같은 팩에 대한 병렬 판단**을 요구한다. 짝 보장, 스키마 위반 시 전체 거부·재요청, 결정 저장소 트랜잭션 — 전부 프로그램 로직이지 대화가 아니다.

같은 이유로 **두 벌 빌드를 기각한다.** 두 번 빌드하면 그 사이에 DB 가 변할 수 있고(브리핑 sync, 배치), 그 순간 "같은 팩에 대한 대응비교"는 문서상으로만 남는다. 순수 파생 함수는 ① 정본이 하나라 감사가 단순하고 ② 시드 팩으로 결정론 테스트가 되고 ③ 과거 팩에 소급 적용해 검증할 수 있다.

### 3. Arm 2 는 종목을 가리는 것이 아니라 제거해야 한다

[ADR 0006](0006-edge-hypothesis.md) 반증 표에서 **F3 의 반증 시 행동이 정확히 "브리핑 채널을 유니버스에서 제거"** 다. Arm 2 는 그 반사실(counterfactual)을 살아야 한다.

종목을 남기고 출처만 가리면, **"이 종목이 시야에 있다"는 사실 자체가 브리핑 유래 정보**라 F3 에 새는 경로가 남는다.

> **누수 카나리아** — Arm 2 응답의 `briefing_refs` 가 비어 있지 않으면 파생 실패다. 게이트에서 하드 거부하고, 그 상태로 되돌아가는 경로를 실패하는 테스트로 막는다.

### 4. 멱등키를 확률적 텍스트 생성기가 만들게 하면 안 된다

현행 `decision.schema.json` 은 `decision_id`·`pack_id`·`generated_at`·`valid_until` 을 **모델의 필수 출력**으로 요구한다(`required` 배열). `decision_id` 는 실행 계층이 중복 주문을 차단하는 멱등키인데([설계안 v1](../00-design-v1.md) [6] 검증 게이트), 그것을 모델이 만들면 재시도할 때마다 다른 키가 나온다. **"같은 id 의 주문은 두 번 나가지 않는다"가 성립하지 않는다.**

러너가 봉인하면 재시도가 같은 키를 재사용하므로 그 성질이 코드로 지켜진다.

### 5. 입력 전문을 저장하는 것이 R6 의 진짜 교훈이다

[03-current-state.md](../03-current-state.md) 3.3 의 R6 는 이렇다.

> 브리핑 프롬프트가 저장소 밖에 있다 | 프롬프트가 바뀌면 과거와 현재 브리핑이 다른 함수의 출력이 되고, **검출할 방법이 없다**

해악은 "밖에 있다"가 아니라 **"함수가 바뀌었는지 검출할 수 없다"** 이다. `pack_id` + 프롬프트 해시 + 렌더러 버전이면 이론상 재구성이 된다. 그러나 이 저장소의 실패 방식은 [CLAUDE.md](../../CLAUDE.md) 첫 장 그대로다 — **동작하지 않는 것과 동작해서 통과하는 것은 겉으로 구분되지 않는다.** 재구성 코드가 돌아가면서 다른 것을 만들어도 알 수 없다.

실제로 보낸 바이트가 남아 있으면 `render_input(pack) == stored_bytes` 라는 **재현 검사가 곧 회귀 테스트**가 된다. 비용은 호출당 15~40KB × 약 600건 ≈ **20MB** 다.

`raw_response` 를 파싱 결과와 따로 두는 근거는 [11.6](../01-context-pack-design.md) 이다 — 파서가 `—` 로 잘라 **근거가 들어 있는 쪽을 버렸고**, 원문이 남아 있었기에 "브리핑 품질 문제"라는 오진을 뒤집을 수 있었다. 결정 파서에 같은 급의 버그가 나면 원문 없이는 과거 판단이 영구히 오염된 채 남는다.

### 6. 재현성을 파라미터로 살 수 없다

최신 모델군은 **`temperature` 등 샘플링 파라미터가 제거**됐다(전달 시 400). "temperature=0 으로 재현성 확보"는 선택지가 아니다. [ADR 0003](0003-ai-decides-last.md) 이 이미 감수한 비결정성을 설계가 전제해야 하고, 그래서 재현의 단위가 **출력의 동일성이 아니라 입력의 증명 가능성**이 된다. 결정 3 이 그것이다.

### 7. 비용은 이 설계의 제약이 아니다

3개월 페이퍼 ≈ 65거래일 × 4사이클 × 2호출(Arm 1·2) = **520건**, 이벤트 사이클·재시도를 더해 600~900건. 입력은 시스템 프롬프트 ~2k + 팩 4~11k(실측 팩 4,153 토큰 / 설계 예산 11,000 — [01-context-pack-design.md](../01-context-pack-design.md) 2장), 출력 1~3k.

Claude API 정가 기준 **3개월 총 $60~170** 규모다. [ADR 0003](0003-ai-decides-last.md) 이 감수 항목으로 든 비용은 유니버스 상한(60)과 팩 축약이 이미 지불했다.

## 함께 확정하는 것

### 스키마 개정 (선행 작업) *(구현 완료 2026-08-30)*

[CLAUDE.md](../../CLAUDE.md) 판단 계층 규칙이 **"스키마를 먼저 고친다"** 이다. 판단 엔진 코드보다 이것이 먼저다.

1. **계약 분리** — 모델 출력은 `market_view`·`abstain`·`abstain_reason`·`decisions`·`portfolio_note`·`data_concerns` 로 줄인다. `decision_id`·`pack_id`·`generated_at`·`valid_until` 은 러너가 봉인한다
2. **`arm` 추가** — 스키마 어디에도 없다. 저장 계층 컬럼으로 넣는다
3. **`invalidation` 구조화** — 아래
4. **구조화 출력 적합성** — 아래

### `invalidation` 을 감시 가능한 형태로

[03-current-state.md](../03-current-state.md) 3.2 는 `invalidation_hit` 을 1로 바꾸는 UPDATE 가 저장소에 없다고 적었다. **이유는 게으름이 아니다** — `"주가가 빠지면"` 같은 자유 문장은 기계가 감시할 수 없다.

[ADR 0003](0003-ai-decides-last.md) 원칙 4("실행 계층이 감시 조건으로 등록한다")가 실현되려면 작은 조건 문법이 필요하다.

```
{ type: price_below | close_below_ma | disclosure_category | stance_reversal,
  value, deadline }   + 자유 텍스트 근거 병기
```

구조화하면 "동어반복·양방향 금지"가 프롬프트 부탁이 아니라 **enum 제약**이 된다. enum 에 없는 조건은 자유 텍스트 + `deadline` 으로 받되 **"감시 불가" 플래그를 남긴다** — 조용히 통과시키지 않는다.

문자열 휴리스틱 검사("또는" 포함 금지 같은)는 **틀린 이유로 통과하는 가드**가 되기 쉬워 차선책으로만 둔다.

### 구조화 출력을 쓴다

API 의 `output_config.format`(JSON 스키마 강제)에 `decision.schema.json` 을 넘기면 **생산자와 검증자가 동시에 생긴다.**

단, 현행 스키마는 그대로 쓸 수 없다. strict 모드는 모든 객체에 `additionalProperties: false` 와 전체 `required` 를 요구하는데 **부적합 지점이 10곳**이다.

| 위치 | 문제 |
|---|---|
| root | `model`·`portfolio_note`·`abstain_reason`·`data_concerns` 가 required 아님 |
| `$defs.decision` | `entry`·`stop`·`target`·`trail`·`weight_pct` 등 9개 |
| `entry` / `stop` / `target` / `trail` | 하위 필드 전부 |
| `$defs.decision.allOf[0..1].if` | `additionalProperties` 미설정 + `required` 없음 |

특히 **`allOf` + `if/then` 조건부 검증은 strict JSON schema 가 지원하지 않는다.** 선택 필드를 nullable 로 바꿔 전부 `required` 에 넣는 방식으로 재작성한다 — `weight_pct` 가 이미 `["number","null"]` 로 그렇게 돼 있으니 패턴은 있다.

### 의미 검증층 — 스키마는 형식만 본다

[11.9](../01-context-pack-design.md) 의 교훈이 **"값의 정합성을 보는 층이 따로 필요하다"** 였다. 엔진 안에 두고, 실패 시 전체 거부·재요청한다. 검증 게이트(블록 C)의 선행 축소판이다.

| # | 검사 | 스키마가 못 잡는 이유 |
|---|---|---|
| 1 | `BUY`/`ADD` 의 code ∈ **그 arm 의 실제 입력** universe (정본 팩이 아니다) | 환각 종목·팩에 없는 종목 |
| 2 | `HOLD`/`TRIM`/`EXIT` 의 code ∈ positions · `BUY` code ∉ `blocked_codes` ∉ 보유 | 보유 종목 BUY, 미보유 EXIT |
| 3 | `weight_pct` ≤ 한도 · BUY 건수 ≤ `max_new_entries_this_cycle` · 결과 포지션 수 ≤ `max_positions` · 주문금액/`adv20_eok_krw` ≤ `max_order_vs_adv_pct` · 섹터 합산 ≤ 한도 | **여기서 `constraints` 가 처음으로 통보에서 강제로 바뀐다** |
| 4 | LIMIT price 가 현재가 ±상식 밴드 · stop 이 진입가 아래 · target > 진입가 | 물리적으로 불가능한 값 |
| 5 | `briefing_refs` ∈ 입력의 briefing_id 집합. **Arm 2 에서 비면 안 됨이 아니라, 비어 있지 않으면 파생 누수** | 근거 3 의 카나리아 |
| 6 | `stop_reason != end_turn`(특히 `max_tokens`·`refusal`)이면 부분 파싱 금지, 전체 거부 | 잘린 JSON 이 우연히 유효할 수 있다 |

`name` 은 모델 출력을 믿지 않고 `listing` 기준으로 러너가 덮어쓴다 — **code 가 진실이다.**

> 각 검사마다 **"위반이 실제로 거부되는" 픽스처 테스트**를 함께 커밋한다(팩에 없는 종목을 답하는 가짜 응답 등). 통과하는 것을 보는 것으로는 부족하다.

### `abstain` 과 장애를 분리한다

**`abstain` 은 판단의 *결과*("살 것이 없다"는 정보)이고, API 장애는 판단의 *부재*다.** 한 필드에 섞으면 F2·F3 대응비교에서 "모델이 관망을 택한 날"과 "API 가 죽은 날"이 같은 값이 된다. 통계에서 abstain 은 관측이고 장애는 결측이다.

| 실패 | 대응 |
|---|---|
| 429 · 5xx · 네트워크 | SDK 자동 재시도 + 엔진 한정 재시도. **사이클 마감 시각**을 넘기면 `timeout` 으로 기록하고 포기 — 낡은 판단을 장중에 집행하는 것보다 신규 진입 없음이 안전하다 |
| 스키마 위반 | 위반 내용을 붙여 **같은 `decision_id` 로** 1~2회 재요청. 소진 시 `schema_rejected`. 모든 시도가 남는다 — **재시도율 자체가 프롬프트 품질 지표다** |
| `stop_reason=max_tokens` | 전체 거부. 스트리밍 + 충분한 `max_tokens` 로 예방 |
| `stop_reason=refusal` | `api_error` 로 기록. 판단 없음 |
| `valid_until` 경과 후 도착 | `expired`. 집행 금지 |
| **한쪽 arm 만 실패** | 성공한 arm 은 정상 집행(Arm 1 이 본선). 다만 그 사이클은 **대응비교 쌍에서 제외 표시** — 짝 없는 관측을 쌍으로 세면 McNemar 가 오염된다 |

### 동결 정책

페이퍼 기간 중 **프롬프트·모델·렌더러는 동결이 기본**이다. 바꿔야 하면 새 `prompt_id` 로 커밋하고, F2·F3 표본 집계를 `(prompt_id, model)` 층으로 분리한다 — **층이 갈리면 불일치쌍 85건 시계가 층별로 다시 간다**([ADR 0005](0005-backtest-scope.md) 표본 계산). 이 비용이 프롬프트를 함부로 안 바꾸게 만드는 올바른 압력이다.

같은 이유로 **페이퍼 중 모델 다운그레이드를 금지한다.** 비용 절감이 아니라 F2 가 검정하는 대상 자체를 바꾸는 행위다.

프롬프트 파일에는 휘발성 값(날짜·시각·계좌 숫자)을 넣지 않는다 — 전부 팩에 있다. [CLAUDE.md](../../CLAUDE.md) 하드 규칙 3(리스크 한도 값 저장소 금지)이 프롬프트 파일에도 적용된다. 한도는 팩의 `constraints` 로 전달되지 프롬프트에 적지 않는다.

### 선행 조치 — 팩을 불변으로 만든다 *(구현 완료 2026-08-30)*

`decision/pack.py` 의 `save()` 가 `ON CONFLICT(pack_id) DO UPDATE SET ... payload=excluded.payload` 다. `pack_id` 는 `YYYYMMDD-HHMM-cycle`(분 단위)이므로 **같은 분에 재빌드하면 payload 가 조용히 덮인다.**

지금은 무해하다. 그러나 결정이 `pack_id` 를 참조하는 순간 **감사 사슬의 첫 고리가 끊긴다** — "이 판단이 무엇을 보고 내려졌는가"를 증명할 수 없다. 백테스트 리플레이에서는 더 위험하다.

두 가지를 같이 한다.

1. 결정 행에 `pack_sha256` 을 봉인해 덮어쓰기를 **검출 가능**하게 한다
2. `save()` 를 **"결정이 참조하는 팩은 불변"** 으로 고친다(해당 팩에 결정이 존재하면 덮어쓰기 거부)

## 감수하는 비용

- **API 장애·429·타임아웃·부분 응답이 저장소가 직접 다뤄야 할 실패 모드가 된다.** 외부 세션이었다면 남의 문제였을 것들이다
- **Arm 2 유니버스가 Arm 1 보다 좁다.** 이는 결함이 아니라 측정 대상("브리핑이 없는 시스템")의 정의이지만, Arm 1 이 브리핑 전용 종목을 골랐을 때 Arm 2 는 같은 종목으로 응답할 수 없다는 **비대칭**이 남는다
- **`invalidation` 구조화는 표현력을 잃는다.** "자사주 매입 중단 공시" 같은 미묘한 조건을 enum 에 욱여넣게 된다. "감시 불가" 플래그가 그 절충이다
- **`derive_arm2` 는 스키마가 바뀔 때마다 같이 손봐야 하는 유지 지점**이 하나 늘어난다
- **append-only 라 잘못된 결정 행도 영구히 남는다.** 정정은 새 행 + 참조로 한다. 저장이 단순해지는 대신 조회(최신 유효 결정 선별)가 한 단계 복잡해진다
- **"사이클 마감 시각을 넘기면 판단 없음"** 은 장 급변일에 판단이 비는 위험을 감수하는 것이다. [ADR 0003](0003-ai-decides-last.md) 이 이미 "판단 지연"을 감수 항목으로 적었고, 보완책(기계적 손절)은 블록 C·D 의 몫이다
- **동결 정책은 프롬프트 개선 속도를 느리게 한다.** 의도된 마찰이다

## 재검토 조건

- **F2 가 기각되면**(AI 선택이 기계적 랭킹을 넘지 못하면) 이 ADR 이 정당화하는 구조 대부분이 불필요해진다. [ADR 0006](0006-edge-hypothesis.md) F2 의 행동("AI 판단 엔진을 축소하고 규칙 비중을 늘린다")이 이 ADR 에 우선한다
- **의미 검증층에서 거부되는 비율이 높게 유지되면**(예: 사이클당 재시도가 상시 발생) 원인이 프롬프트인지 스키마인지 팩인지를 먼저 가른다. 재시도로 덮지 않는다
- **`invalidation` 의 "감시 불가" 비율이 높으면** enum 을 늘릴 것인지, 자유 텍스트를 포기할 것인지를 다시 본다. 감시되지 않는 무효화 조건은 [ADR 0003](0003-ai-decides-last.md) 원칙 4 를 형식적으로만 만족시킨다
- **[설계안 v1](../00-design-v1.md) 7장 1번(실행 계층을 클라우드에 둘 것인가)** 이 정해지면 호출 위치가 다시 논점이 될 수 있다. 다만 "도구 없는 봉인 호출"이라는 성질은 위치와 무관하게 유지한다
