# AI 매매 시스템 설계안 v1 — 조사 결과 및 아키텍처

작성일: 2026-08-20
전제 수정: K-Trader는 **참고 자산**으로만 쓰고 신규 구축. AI가 매수·보유·매도를 **종합 판단**하며, 정량 지표와 브리핑은 판단의 **입력**이지 필터가 아님.

## 1. 키움 조건검색식 — 실제 활용 범위 (조사 완료)

### 1.1 할 수 있는 것

조건 대분류 6개: **범위지정 / 시세분석 / 기술적분석 / 패턴분석 / 재무분석 / 순위분석**

| 영역 | 지원 범위 |
|---|---|
| 기술적 지표 | MACD, RSI, 볼린저밴드, 스토캐스틱, CCI, DMI/ADX, 일목균형표, OBV, MFI, Envelope, Parabolic, TRIX, Williams %R 등. 이동평균은 6종 계산방식(단순/지수/가중/기하/조화/삼각) |
| 가격·거래량 | 신고가·신저가, 갭 발생·돌파, 거래량 급증, 거래대금, 이격도, 전고점 돌파, 매물대 돌파, 체결강도, 호가잔량 |
| 수급 | 외국인·기관·개인·연기금·국가 및 조합. 순매수 일수/수량/금액/누적, 상장주식수 대비 비율. 프로그램매매 순매수·증감. **공매도 거래량·비중·평균가 대비 등락률**. **대차잔고 증감·유통주식수 대비 비중**. 거래원별 순매매 |
| 재무 | PER, PBR, PSR, PCR, EV/EBITDA, PEG, ROE, ROA, 영업이익률, 매출액·영업이익·순이익 증감률, 부채비율, 이자보상배율 |
| 조합 | AND / OR / NOT, **괄호 중첩 가능**. 단 괄호 사용 시 순차검색 불가 |
| 종목 필터 | 정리매매·관리·투자위험·투자경고·환기·단기과열 제외. 우선주·ETF·REITs 구분 |

### 1.2 하드 제약 — 여기가 판정의 근거

| # | 제약 | 영향 |
|---|---|---|
| 1 | **조건식 생성·수정은 영웅문4(Windows HTS)에서만.** API로 생성·수정·조회 불가. 키움 공식 문구: *"조건검색은 영웅문4에서 만드실 수 있습니다."* | **코드로 버전관리·파라미터 스윕이 불가능.** 정량 레이어의 본체로 삼을 수 없는 결정적 이유 |
| 2 | **최소 판정 주기 1분.** 공식 FAQ: *"조건식에서는 최소 주기가 1분 단위이므로 순간체결량 조건은 설정 불가"* | 틱/초 단위 진입 타이밍 불가 |
| 3 | **실시간 조건검색 세션당 10건** (공식 유량 문서) | 병렬 전략 11개 이상 불가 |
| 4 | **조건검색 결과 최대 100종목 노출.** OpenAPI+ 개발가이드: *"조건검색 결과가 100종목을 넘게 되면 실시간 조건검색을 할 수가 없습니다."* | 광범위 스크리닝의 실시간화 불가. 조건을 계속 조여야 함 |
| 5 | **재무는 최근 결산·최근 분기만.** 공식 FAQ: *"이전 기간에 대한 조건식을 설정할 수 없습니다"* | 흑자전환, 2분기 연속 개선 같은 조건 **불가**. 데이터는 FnGuide 제공, **실적 발표 후 2~3주 지연** |
| 6 | **당일 투자자 수급은 장 종료 후 제공** | 장중 수급 필터 불가 |
| 7 | **분봉 주기는 수정주가 미반영** | 액면분할·유증 종목에서 오작동 |
| 8 | **조건식 하나에 조건 20개 상한**, HTS 검색결과 보관 682종목 | |
| 9 | **백테스트 불가** — 과거 시점의 조건 만족 여부를 재현할 수단 없음 | |
| 10 | 조건만족시간 필드는 **재편입 시 최초 시각을 덮어씀** | 이벤트 이력을 조건검색에 의존 불가. 자체 로깅 필수 |

### 1.3 판정

**조건식은 정량 레이어의 본체가 될 수 없습니다.** 제약 1(코드 버전관리 불가), 5(재무 1기만), 9(백테스트 불가) 세 가지가 결정적입니다. 재현 불가능한 블랙박스를 시스템의 뼈대로 두면 성과가 나빠졌을 때 원인을 분리할 수 없습니다.

**다만 버릴 것도 아닙니다.** 조건식이 유일하게 잘하는 일이 하나 있습니다 — **실시간 편입 푸시**. 키움 REST의 `ka10173`은 조건 만족 순간 WebSocket으로 밀어줍니다(한국투자증권은 폴링만 지원). 전 종목을 1분마다 재계산하는 비용을 키움 서버에 떠넘길 수 있습니다.

→ **결론: 정량 계산은 클라우드에서 자체 수행(안 B), 조건식은 "장중 이벤트 감지 센서"로 보조 사용.**

## 2. API 기반 — 키움 REST로 가야 합니다

키움 REST API가 2025년 3월 24일 출시됐습니다. 기존 OpenAPI+와의 차이가 이 프로젝트의 성패를 가릅니다.

| 항목 | OpenAPI+ (현 K-Trader) | **키움 REST API** |
|---|---|---|
| 방식 | 32bit COM/OCX, ActiveX | REST + WebSocket |
| OS | **Windows 전용** | **멀티 OS 공식 명시 (윈도우·맥·리눅스)** |
| 설치 | OCX 레지스트리 등록 | **미설치형** |
| 로그인 | **HTS 로그인 창(GUI) 필수** | 앱키/시크릿 → OAuth 토큰 |
| Python | **32비트 강제** | 64비트 자유 |
| ML/LLM 라이브러리 | **사실상 불가** | 제약 없음 |
| 클라우드 24h 무인 | 불가 | **가능** |
| 과거 차트 | opt10079~94 | ka10079~94, **연속조회 + 수정주가 선택** |
| 조건검색 | 실시간 지원 | **실시간 푸시 지원 (ka10171~10174)** |
| 실시간 시세 | 화면 200 × 종목 100 | **세션당 200종목** |
| 유량 | 초당 5 / 분당 100 / 시간당 1,000 | **초당 5** (분·시간 한도 없음) |
| 모의투자 | 명시 없음 | **지원 (KRX만, 유량 TR당 초당 1회)** |
| 국내 선물/옵션 | 지원 | **미지원** |

**32비트 탈출만으로 이전 근거가 충분합니다.** AI 판단 중심 프로그램에서 32비트 프로세스는 사형선고입니다.

주의사항 3가지:
1. **국내 선물/옵션이 필요하면 키움 REST로는 불가.** 주식 스윙만 한다면 무관.
2. **조건식 생성은 여전히 영웅문4 필요.** 단 만들 때만 Windows가 필요하고, 런타임 조회·구독은 리눅스에서 가능. 상시 상주 불필요.
3. **3개월간 실서버 미접속 시 서비스 자동 해지.** 모의투자만 쓰는 개발 기간이 길어지면 해지됩니다.

대안 비교: 한국투자증권 KIS는 상품 커버리지가 넓고(국내 선물옵션, 해외선물) 리눅스 가능하지만 **조건검색이 폴링만 지원**하고 WebSocket 등록 종목 수가 불리하다는 비공식 보고가 있습니다. LS증권 OPEN API는 **조건검색 연동 자체가 없습니다**(스크리너만 제공).

## 3. 데이터 소스 — 2026년의 지형이 바뀌었습니다

### 3.1 가장 중요한 변화: KRX가 로그인 벽을 세웠습니다

**2025-12-26부터 data.krx.co.kr이 로그인 없이는 통계 데이터를 주지 않습니다.** 실측 결과 전종목 시세, CSV 다운로드 OTP 등 주요 엔드포인트가 모두 `LOGOUT` 응답. 공매도종합포털(short.krx.co.kr)도 같은 벽 뒤로 리다이렉트됩니다.

- **pykrx 1.2.8은 이제 `KRX_ID` / `KRX_PW` 환경변수가 필수**입니다. 없으면 대부분의 함수가 빈 DataFrame이나 KeyError를 반환합니다. (GitHub 마일스톤 "KRX 로그인 방식 변경 대응" 2026-01-31 완료)
- 대체로 열린 **KRX Open API(openapi.krx.co.kr)** 는 일봉 OHLCV만 있고 **투자자별 수급·프로그램매매·공매도·시가총액 시계열·PER/PBR이 전혀 없습니다.** 게다가 약관 제6조 ②가 **상업적 이용을 금지**합니다.

### 3.2 실제로 쓸 수 있는 조합 (전부 실측 검증됨)

### 3.3 분봉 — 무료 소급 수집 불가

- 네이버 분봉은 **최근 6거래일치뿐이고 시가·고가·저가가 전부 null**입니다.
- KIS·키움 REST 모두 **당일 분봉만** 제공.
- 유료 대안: KRX 데이터 상품 1년치 약 30만원 (2차 출처 기준, 최신 가격 확인 필요)

→ **오늘부터 매일 장 마감 후 당일 분봉을 적재해 스스로 축적**하는 것 외에 방법이 없습니다. 클라우드 크론에 적합. 지금 시작하면 3개월 뒤에는 60거래일치가 쌓입니다.

### 3.4 정합성 함정 3개

1. **소스를 섞지 마세요.** 네이버·FDR은 수정주가, KRX Open API·pykrx(`adjusted=False`)는 원본가입니다. 액면분할 종목에서 수익률이 50배 튑니다.
2. **거래정지일 0값 행.** 삼성전자 2018-04-30~05-03이 `시가=고가=저가=0, 거래량=0, 종가=전일종가`로 들어옵니다. 그대로 지표에 넣으면 ATR·볼린저·RSI가 오염됩니다. `Open>0 & Volume>0` 필터 필수 — 동시에 이게 **거래정지일 판별 신호**로도 쓰입니다.
3. **pykrx 수정주가는 "요청 구간 마지막 날 기준"으로 재계산**됩니다. 캐시를 증분 갱신하면 분할 이벤트 후 조용히 불일치가 쌓입니다. 분할·증자 발생 시 해당 종목 전체 재적재 필요.

## 4. 아키텍처 — AI 판단이 마지막에 오는 구조

### 4.1 잘못된 순서와 올바른 순서

```
[잘못됨]  AI가 후보 선정 → 정량 조건 확인 → 진입
          → AI는 후보 생성기로만 쓰이고, 실행 판단은 규칙이 함
          → "보유 중 악재 발생 → 청산" 같은 종합 판단 불가

[올바름]  정량 계산 + 브리핑 + 계좌·포지션 상태 → 컨텍스트 팩
          → AI가 매수·보유·매도를 한 번에 종합 판단
          → 실행 계층이 검증·리스크 한도·주문 집행
```

핵심은 **AI가 보는 것이 "후보 목록"이 아니라 "시장 상태 + 내 포트폴리오 전체"** 라는 점입니다. 그래야 "A를 사려면 B를 먼저 줄여야 한다", "C는 지표는 좋지만 오늘 브리핑의 섹터 역풍과 충돌한다" 같은 판단이 나옵니다.

### 4.2 전체 구조

```
┌─ 클라우드 (리눅스, 24h) ────────────────────────────────────┐
│                                                            │
│  [1] 데이터 계층 (배치)                                      │
│      네이버 일봉 · 수급 / DART 공시 / 키움 REST 분봉·프로그램  │
│      → PostgreSQL 또는 SQLite (일봉·지표·수급·공시)          │
│      → TA-Lib로 지표 계산 → 종목별 지표 벡터                  │
│                                                            │
│  [2] 브리핑 계층 (기존 6종 유지 + 구조화)                     │
│      텍스트 브리핑 → JSON 구조화                             │
│      {code, 관점, 확신도, 촉매유형, 틀리는조건, 출처}          │
│                                                            │
│  [3] 컨텍스트 팩 빌더                                        │
│      [1]+[2]+계좌상태+포지션+최근 판단이력 → 단일 컨텍스트     │
│                                                            │
│  [4] AI 판단 엔진  ★ 여기가 시스템의 뇌                       │
│      입력: 컨텍스트 팩 / 출력: 구조화된 결정 JSON             │
│      매수·추가매수·보유·축소·청산을 한 번에 결정               │
│                                                            │
│  [5] 결정 저장소 (append-only, 감사 추적)                    │
│      decision_id, 근거, 무효화 조건, 만료시각                 │
└────────────────────────┬───────────────────────────────────┘
                         │  서명된 결정 (HMAC + nonce + TTL)
═════════════════════════╪══ 신뢰 경계 ═══════════════════════
                         ▼
┌─ 실행 계층 (클라우드 또는 로컬) ─────────────────────────────┐
│  [6] 검증 게이트 — AI가 넘을 수 없는 벽                       │
│      스키마 · 종목 실재 · 거래정지/관리종목 · VI · 상한가       │
│      비중 상한 · 총 노출 상한 · 일일 손실한도 · 유동성 대비 주문 │
│      멱등성(decision_id 중복 차단) · 킬 스위치                │
│                                                            │
│  [7] 주문 집행기 (키움 REST)                                 │
│      레이트리밋 큐(초당 5, 매도 우선) · 미체결 관리 ·           │
│      예수금 SSOT 재계산 · 체결 정합성                         │
│                                                            │
│  [8] 실시간 감시 (WebSocket)                                 │
│      체결·잔고·VI + 조건검색 편입 푸시(ka10173)               │
│      → 무효화 조건 충족 시 [4]에 재판단 요청 또는 즉시 청산     │
└────────────────────────────────────────────────────────────┘
```

### 4.3 판단 사이클 (기존 브리핑 6종과 정렬)

| 시각(KST) | 단계 | 내용 |
|---|---|---|
| 06:00 | 데이터 배치 | 전일 미국장, 일봉·수급 적재, 지표 재계산 |
| 08:00 | 브리핑 | 한국 장전 심층분석 (기존) |
| **08:20** | **AI 진입 판단** | 정량 + 브리핑 + 계좌 → 오늘의 매수 후보와 진입 조건, 보유 종목 처리 방침 |
| 09:00~15:20 | 실행 | 실행 계층이 집행. 조건식 편입 푸시·VI·손절선 접근 시 **이벤트 재판단** |
| 12:00 | 브리핑 | 오전장 총평 (기존) |
| **12:20** | **AI 중간 점검** | 보유 종목 유지/축소/청산, 오전 흐름 반영 |
| 14:50 | 브리핑 | 장마감 전 점검 (기존) |
| **15:00** | **AI 종가 판단** | 오버나이트 보유 여부, 종가 청산 대상 |
| 18:00 | 브리핑 | 장마감 종합 (기존) |
| **18:30** | **AI 복기** | 판단 로그 vs 실제 결과 대조, 오판 패턴 기록 |

**정기 판단 4회 + 이벤트 재판단**. 장중 상시 호출은 비용·지연·일관성 모두에서 불리합니다.

### 4.4 AI 출력 스키마 (강제)

```json
{
  "decision_id": "20260821-0820-a3f9",
  "valid_until": "2026-08-21T15:20:00+09:00",
  "market_view": "한 문단",
  "decisions": [
    {
      "action": "BUY | ADD | HOLD | TRIM | EXIT",
      "code": "005930",
      "name": "삼성전자",
      "weight_pct": 8.0,
      "entry": { "type": "MARKET | LIMIT | COND", "price": null, "condition": "시가 대비 -1% 이하" },
      "stop":   { "type": "ATR | PCT", "value": 2.0 },
      "target": { "type": "ATR | PCT", "value": 3.5 },
      "max_hold_days": 7,
      "confidence": "상 | 중상 | 중 | 하",
      "reasons": ["출처 확인된 사실 2개 이상"],
      "invalidation": "반증 가능한 단일 사건",
      "sources": ["url"]
    }
  ],
  "abstain": false,
  "abstain_reason": null
}
```

**`abstain` 필드가 중요합니다.** AI가 "오늘은 진입할 만한 것이 없다"고 말할 수 있어야 합니다. 후보를 반드시 N개 채우게 만들면 근거 없는 종목으로 자리를 메웁니다 — 기존 브리핑 프롬프트가 이미 이 규칙을 갖고 있습니다.

`invalidation`은 브리핑의 '틀리는 조건'과 같은 형식입니다. **반증 가능한 단일 사건**이어야 하고, 실행 계층이 이걸 감시 조건으로 등록합니다.

### 4.5 실행 계층이 AI를 신뢰하지 않는 지점

AI 출력은 **제안**이고, 아래를 통과해야 주문이 나갑니다.

| 검증 | 내용 |
|---|---|
| 스키마 | JSON 스키마 강제, 필드 누락 시 전체 거부 |
| 종목 실재 | 6자리 코드 + 종목 마스터 대조 (환각 방지) |
| 거래 가능성 | 거래정지·관리종목·투자경고·정리매매 제외 |
| 유동성 | 주문금액 ≤ 20일 평균 거래대금 × 상한비율 |
| 비중 | 종목당 상한, 섹터 집중도 상한, 총 노출 상한 |
| 손실 | 1회 최대 손실(계좌 대비 %), 일일 손실한도 도달 시 신규 진입 차단 |
| 멱등성 | `decision_id` 중복 주문 차단, `valid_until` 만료 시 폐기 |
| 킬 스위치 | 단일 플래그로 전체 정지 |

**완전 자동 주문은 이 게이트가 전부 검증된 뒤 스위치로 켭니다.** 초기에는 꺼두고 텔레그램 승인을 거치는 편이 안전합니다.

## 5. K-Trader에서 계승할 자산

3년치 실전 디버깅이 녹아 있는 부분들입니다. 코드를 가져오는 게 아니라 **설계 원칙을 가져옵니다.**

| 계승 | 이유 |
|---|---|
| **예수금 SSOT 재계산** (`_compute_locked_deposit`) | 누적 카운터 대신 미체결 주문에서 매번 재계산. 드리프트 원천 차단. 신규 시스템에서는 **모든 상태에 이 패턴을 적용** |
| **주문 레이트리밋 큐 + 매도 우선순위** (`tr_scheduler`) | 조회 지연이 손절 주문을 막지 않게 큐를 분리. 키움 REST도 초당 5회 제한이라 그대로 필요 |
| **HARD-STOP 이중 안전망** | 일반 손절과 별개로 항상 켜진 비상 손절. 시장가 강제 재발행 |
| **매도 무한 재시도** | VI 발동 시 매도가 체결될 때까지 취소→시장가 재발행 반복 |
| **매도 전 미체결 매수 취소** | 유령 포지션 방지 |
| **잔고 대사(reconciliation)** | HTS 잔고와 로컬 상태 주기적 교차검증, 고착 주문 정리 |
| **발주~접수 공백 예수금 잠금** | 체결 통보 전 구간의 이중 사용 방지 |
| **원자적 상태 저장** (tmp → os.replace) | 크래시 시 상태 파일 손상 방지 |
| **조건식별 파라미터 폴백 구조** | 신호원별 전략 프로파일 개념. AI 판단 프로파일에 그대로 적용 가능 |

| 버릴 것 | 이유 |
|---|---|
| 단일 클래스 4,006줄 God Object | 도메인 객체(Position, Order, Signal, Decision)로 분리 |
| **로그 문자열 기반 제어 흐름** | `"손절" in reason` 분기 → Enum |
| 22개 병렬 dict 상태 관리 | 단일 상태 저장소 + 재계산 |
| `config.get(...) or 기본값` | 0/False가 삼켜짐 → 명시적 None 체크 |
| PyQt UI와 엔진의 강결합 | 헤드리스 코어 + 별도 UI |
| 기존 백테스터 | 낙관 편향 5중 누적. 새로 작성 |

## 6. 개발 로드맵

| 단계 | 내용 | 산출물 | 기간 감 |
|---|---|---|---|
| **0** | 키움 REST 앱키 발급, 모의투자 계정, 조건식 실제 제약 실측(10개·100종목) | 검증 노트 | 1주 |
| **1** | 데이터 계층 — 일봉·수급·공시 적재 + TA-Lib 지표 계산 파이프라인. **분봉 일일 적재 즉시 시작** | 데이터 DB + 배치 | 2~3주 |
| **2** | 브리핑 구조화 — 기존 26일치 파싱 → JSON. 이후 브리핑 생성 시 JSON 동시 출력 | 구조화 DB | 1~2주 |
| **3** | 백테스트 엔진 — 정량 규칙만으로. 갭·슬리피지·거래세·거래정지 반영, walk-forward | 검증된 베이스라인 | 3~4주 |
| **4** | AI 판단 엔진 — 컨텍스트 팩 + 출력 스키마 + 페이퍼 실행 | 판단 로그 | 2~3주 |
| **5** | **페이퍼 forward test — 최소 2~3개월** | 성과 리포트 | 2~3개월 |
| **6** | 실행 계층 + 검증 게이트 + 모의투자 주문 | 주문 집행기 | 3~4주 |
| **7** | 소액 실계좌 → 한도 상향 → 완전 자동 | — | 단계적 |

**단계 3과 5는 압축할 수 없습니다.** 3은 정량 뼈대의 기대값을 알기 위해, 5는 AI 판단의 실제 엣지를 재기 위해 필요합니다. 3이 없으면 "AI가 기여한 부분"을 분리할 수 없고, 5가 없으면 검증 자체가 없습니다.

## 7. 남은 결정 사항

1. **실행 계층을 클라우드에 둘 것인가, 로컬에 둘 것인가.** 키움 REST는 클라우드가 가능하지만, 네트워크 장애 시 포지션이 방치되는 위험이 있습니다. 로컬 상주는 안정적이지만 관리 부담이 있습니다.
2. **AI 모델을 어디서 호출할 것인가.** 현재 브리핑 파이프라인처럼 스케줄 세션에서 호출할지, 별도 API 호출 코드를 둘지.
3. **조건식을 쓸 것인가.** 쓴다면 영웅문4에서 조건식을 만들어야 하고, 그 정의를 코드 밖에서 수기로 미러링해야 합니다.
4. **초기 운용 자금과 종목당 최대 손실 한도.** 포지션 사이징 로직의 전제입니다.
5. **기존 K-Trader를 병행 운용할 것인가.** 병행하면 같은 계좌에서 두 시스템이 주문을 내게 되어 예수금·보유한도 충돌이 생깁니다. 계좌 분리 또는 완전 전환이 필요합니다.
